## 1. Activation-site proof (before the corruption)

Hook: `CHAOS/gem5/src/arch/arm/mmu.cc` (`M08` block). A `Request` is translated
(`te->pAddr`, `req->setPaddr(pa)`), then `testAndFinalize()` (permission /
alignment) runs, then, **only when `fault == NoFault`**, the M08 block applies
`new_pa = pa ^ mmu_m08_pa_xor_mask` and calls `req->setPaddr(new_pa)`. The final
outgoing `Request` therefore carries `new_pa`; the TLB entry and its PFN are
not modified. Two details matter for reading the log:

* `old_pfn`/`new_pfn` in the activation event are **the TLB entry’s PFN before
  and after** the hook (`te->pfn`), which is why both are `0x834b6` even though
  `new_pa>>12 = 0x834b7`. That equality is the proof the TLB entry was not
  mutated; `old_pa`/`new_pa` are the Request PA before/after.
* The guest’s own pagemap check independently confirms the same two pages:
  `W10_RESULT pa=0x834b6000 pa_neigh=0x834b7000` in R01B/R02C/R03B/R04B and
  `W10S_RESULT target_pfn=0x83530 neighbor_pfn=0x83531` in R05B2.

## 2. Why the prior R03 trace is unacceptable, and what the new run must contain

Three independent defects:

1. **Wrong-path activation.** The faulted instruction is at PC `0x400d28`,
   which is the **R02 context block** in the exact binary embedded in
   `runs/TEST-M08-R03B/rcS.scoped` (SHA256 `20d9f249…`). R03’s own load is at
   `0x400da4`; it is never traced.
2. **Trace race / invisible consumer.** The MMU trace only starts a
   transaction on a TLB **miss**. The wrong-path translations warm the TLB,
   so the architecturally correct R03 load is a TLB hit and produces no
   event at all. The two traced translations are both uncommitted
   (`squash` 4410, 4447); the guest’s correct `branch=1` comes from the
   untraced hit.
3. **Missing consumer proof.** No `rf_writeback` and no `commit` exist for
   the faulted `dyn_inst_seq`; the summary states `consumed=0`
   (`outcome=activated_not_consumed`). The run cannot show the corrupted
   value steering the `LDR → branch` consumer.

**New R03 run must contain** (all with a fresh `TEST-F1-` ID and the rebuilt
W10):
* `mmu_fault_activate` whose `translation_result` has **`pc = 0x400e1c`**
  (R03’s own `ldrb` in the new build, see §3) — not `0x400d28`;
* `translation_result` + `lsu_request` with `new_pa = old_pa ^ 0x1000`;
* cache/MSHR/`memory_response` on that PA;
* **`rf_writeback` and `commit` of the faulted `dyn_inst_seq`**;
* the consumer branch committing with `branch=2` (corrupted value ≠ expected
  sentinel);
* guest line `observed=<neighbor_sentinel>`, `sentinel != neighbor_sentinel`,
  `branch=2`, `result=FAIL`;
* `rf_writeback`/`commit` must *not* be preceded by a `squash` of that seq.

## 3. Applied workload changes

### 3.1 W10 (`workloads/mmu/W10/mmu_w10.c`)

**Finding.** `run_context()` dispatched on `strcmp(ctx, …)` and every branch
dereferenced the same live pointer `p`. O3 executes the target load of an
earlier context block before the `strcmp` branch resolves. That wrong-path
load performs the cold walk and fills the TLB; the correct-path load then
hits. Measured exactly on R02C/R03B/R04B (§1).

**Fix.** Each context block now loads from its own compile-time constant
`W10_CTX_VA(i) = W10_TARGET + i*0x100000` (the same VA `main()` maps for that
context), and `run_context()` verifies the mapped pointer equals the constant.
A wrong-path block therefore touches a VA that is not mapped in a scoped run
(its speculative abort is discarded, and its TLB fill is for a different VA),
so the selected context’s VA is still cold when its own load executes. The
dynamic consumer semantics are unchanged:

| ctx | instruction (new PCs) | consumer |
|---|---|---|
| R01 | `ldrb` @ `0x400b84`, VA `0x4001000000` | direct sink |
| R02 | `ldrb` @ `0x400df8`, VA `0x4001100000` | `v + 0x11` |
| R03 | `ldrb` @ `0x400e1c`, VA `0x4001200000` | `if (v == expect)` branch |
| R04 | `ldrb` @ `0x400e78`, VA `0x4001300000` (+ dependent `ldrb` @ `0x400e84`) | address dependency |
| R05 | `ld1` (NEON) @ `0x400d58`, VA `0x4001400000` | vector `+1`, lane 0 |
