Two factual corrections to the approved premise, both proven in §3/§6:

1. The kernel's execute-only PTE (`PAGE_EXECONLY`) is **AP[2:1] = 0b10**
   (`PTE_RDONLY=1`, `PTE_USER=0`), not `0b00`. Both values deny EL0 read/write
   in gem5's model; the correct gate is "AP does not grant EL0 read", with
   0b10 being the expected real value.
2. `PROT_EXEC`-only becomes execute-only **only if the CPU advertises
   FEAT_EPAN at runtime** (`ID_AA64MMFR1_EL1.PAN >= 3`). The vendored gem5
   advertises `PAN = 1`; therefore the guest kernel keeps
   `PAGE_READONLY_EXEC` (AP[2:1]=0b11) and R03's EL0 load is **granted**.
   This is a platform blocker, not a workload bug.

## 3. Exact PTE-field proof plan

### 3.1 Where `pte_value` comes from (real implementation)

* `CHAOS/gem5/src/arch/arm/table_walker.cc:2207` calls
  `mmuNotePteDecode(..., curr_state->longDesc.data, ...)` after decoding.
* `CHAOS/gem5/src/cpu/o3/CHAOSPropagation/CHAOSPropagation.cc:3446-3490`
  emits event `kind=pte_decode` with real fields:
  `va`, `pte_address`, `pte_value_before`, `pte_value_after`,
  `walk_level=L1|L2|L3`, `descriptor_type=Table|Page|Block|Invalid`,
  `walk_id`, `translation_id`, `ptw_request_id`.
* `descriptor_type` is derived from the long-descriptor type
  (`table_walker.cc:2200-2206`); at L3, `Page` means `pte_value & 0b11 == 0b11`.
* `pte_value_after` is the decoded descriptor itself (host-order copy; there
  is no PTE write-back path), so it *is* the architectural leaf value that
  the permission decision uses.

### 3.2 ARMv8 4 KiB L3 leaf decode used below

| field | bits | mask |
|---|---|---|
| VALID | [1:0] (leaf = `0b11`) | `v & 0x3` |
| AF | [10] | `(v >> 10) & 1` |
| AP[2:1] | [7:6] | `(v >> 6) & 0x3` |
| UXN | [54] | `(v >> 54) & 1` |
| PXN | [53] | `(v >> 53) & 1` |

### 3.3 Required values

**R03 (target page `0x400d200000`, expected EL0 load denial by AP):**

* `descriptor_type == Page`, `walk_level == L3`, `VALID == 3`, `AF == 1`.
* `UXN == 0` (proves the page is executable; the load denial cannot be XN).
* AP must **not** grant EL0 read:
  * expected real value with EPAN: `AP[2:1] == 0b10` (the kernel's
    `PAGE_EXECONLY` constant, see below);
  * `AP[2:1] == 0b00` is also a deny and may be accepted as evidence;
  * `AP[2:1] == 0b01` or `0b11` → **BLOCKED_R03_AP** (EL0 read is allowed;
    with `0b11` the realization is the non-EPAN `PAGE_READONLY_EXEC`).
* The `pte_decode` must appear **after** the `mprotect` TLBI group
  (`tlbi_issue`/`tlbi_match`/`tlbi_invalidate` for the VA) and **before**
  `mmu_fault_activate` for the same VA.
* Then require, in order:
  `permission_eval va=0x400d200000 permission_result=deny mode=Read` →
  `mmu_fault_activate va=0x400d200000 mode=Read permission_before=false
  permission_after=true`.
* If instead the trace shows `descriptor_type=Invalid`, `VALID != 3`, or no
  `permission_eval`/`activate`, the run took a translation path →
  **BLOCKED_R03_TRANSLATION** (exactly the old R03B failure, §3.5).

**R05 (target page `0x400d600000`, fetch `0x400d600180`):**

* `descriptor_type == Page`, `walk_level == L3`, `VALID == 3`, `AF == 1`.
* `UXN == 1` (the XN decision that denies the EL0 fetch).
* `AP[2:1]` should be `0b11` for a shared `PROT_READ` file mapping
  (`PAGE_READONLY`); `0b10` would also be a read-only encoding and is
  acceptable. `AP == 0b01` (writable) would not be the frozen design.
* If the trace contains only the populate-walk `pte_decode` (before
  `mprotect`) and no post-TLBI leaf decode, that is acceptable for the XN
  proof **provided the quoted PTE has UXN=1** (the same bit the fetched
  `TlbEntry` carries), but the report must say so explicitly.
* Then require
  `permission_eval va=0x400d600180 permission_result=deny mode=Execute` →
  `mmu_fault_activate va=0x400d600180 mode=Execute permission_before=false
  permission_after=true`.
* On the injected run, require the trace to reach a fetch/commit of the
  target and the workload line `W14_INFO stage=executed marker=0x5a` +
  `injected_success=1 value_ok=1 observed=0x5a`.
* If `UXN == 0` or the leaf is `Invalid` → **BLOCKED_R05_UXN**.

### 3.4 How a real AP permission fault is distinguished from a translation fault

Workload-side (necessary, not sufficient):

* `si_code == SEGV_ACCERR (2)` for the permission path,
  `SEGV_MAPERR (1)` for the translation path;
* `pte_present == 1` from `/proc/self/pagemap` (a valid leaf exists);
* `fault_addr` equals the target VA / target PC.

**`si_code` alone is not sufficient.** The old R03B run proves it: a
translation fault on the `PROT_NONE` (invalid `PTE_PROT_NONE`) encoding was
still delivered as `si_code=2` (Linux checks the VMA rights). The
authoritative discriminator is `pte_decode`:

```

          pte_value_after=460000083577f82 descriptor_type=Invalid
event 407 kind=mmu_fault_unactivated
```

Decode of `0x460000083577f82`: `VALID = 2` (not `0b11`), AP[2:1]=`0b10`,
UXN=1 → at L3 this is `Invalid` (the `PTE_PROT_NONE` bit[1]), i.e. a
**translation fault**, yet the workload printed `si_code=2`.

Real reference value for a valid XN leaf in this guest (old R04B populate
walk):


Decode of `0x68000083577fc3`: `VALID=3, AF=1, AP=0b11, UXN=1, PXN=1` — the
`PAGE_READONLY` shared-file leaf. R05 must produce the analogous leaf for
`0x400d600000` with `UXN=1`.

### 3.6 The kernel constants that make R03 blocked (static proof)

Extracted directly from `gem5-fs/vmlinux` (not assumed):

```
protection_map (default, before adjust_protection_map):
index  4 (EXEC):        0x0020000000000fc3  VALID=3 AP=0b11 UXN=0 PXN=1
index 12 (EXEC|SHARED): 0x0020000000000fc3  VALID=3 AP=0b11 UXN=0 PXN=1
```

`adjust_protection_map` (disassembly):

```
ffffffc008aa5a7c <adjust_protection_map>:
  ldr  x0, [x0, #1288]      ; cpu_hwcaps
  tst  w0, #0x8000          ; ARM64_HAS_EPAN == bit 15
  b.eq ...                  ; not supported -> keep the defaults above
  mov  x1, #0xf83
  movk x1, #0x20, lsl #48   ; 0x0020000000000f83
  str  x1, [x0, #32]        ; protection_map[4]  = PAGE_EXECONLY
  str  x1, [x0, #96]        ; protection_map[12] = PAGE_EXECONLY
```

`PAGE_EXECONLY = 0x0020000000000f83` decodes as
`VALID=3 AF=1 AP[2:1]=0b10 UXN=0 PXN=1` — a valid, executable, EL0-unreadable
leaf (the correct R03 target).

Which capability is bit 15, and what sets it (gdb on the shipped vmlinux):

```
EPAN ftr entry: capability=15, sys_reg=ID_AA64MMFR1_EL1,
                field_pos=20 (PAN field), min_field_value=3
```

gem5's reset for that register
(`CHAOS/gem5/src/arch/arm/regs/misc.cc:5806-5814`):

```cpp
mmfr1_el1.pan = release->has(ArmExtension::FEAT_PAN) ? 0x1 : 0x0;
```

and the Param default (`ArmISA.py`): `id_aa64mmfr1_el1 = 0x0000000000101020`
→ PAN field `[23:20] = 1`. A search for `epan` across
`CHAOS/gem5/src/` returns nothing. Therefore the gem5 guest advertises
`PAN <= 1 < 3`, `ARM64_HAS_EPAN = false`, `protection_map[4/12]` stays
`PAGE_READONLY_EXEC` (AP=0b11, readable), and R03's EL0 load is granted.

## 6. Honest risks / blockers

### 6.1 BLOCKER B-C1 (R03): the gem5 platform does not advertise FEAT_EPAN

*Proof chain*: kernel `protection_map[4/12] = 0x0020000000000fc3`
(`AP=0b11`, readable) → `adjust_protection_map` only replaces it with
`PAGE_EXECONLY` (`AP=0b10`) when `cpu_hwcaps` bit 15 (`ARM64_HAS_EPAN`) is
set → that capability requires `ID_AA64MMFR1_EL1.PAN >= 3` (gdb-decoded
`arm64_features` entry: sys_reg=ID_AA64MMFR1_EL1, field_pos=20, min=3) →
gem5's reset writes `PAN = FEAT_PAN ? 1 : 0` and has no FEAT_EPAN at all →
`PROT_EXEC`-only stays `PAGE_READONLY_EXEC`, so the EL0 load is granted.

*Observable symptom*: the R03 control completes the load
(`injected_success=1 result=FAIL pte_present=1`) with no
`permission_eval`/`mmu_fault_activate`; the trace leaf is
`descriptor_type=Page VALID=3 AP=0b11 UXN=0`. The host native run exhibits
exactly this today.

*Status*: **R03 cannot be closed on the current frozen binary.** Do not
transcribe AP=0b00 or claim a pilot pass. Do not substitute PROT_NONE
(translation fault — the old rejected design).

*Options (require the researcher/Main; Agent C must not implement)*:

1. **Enable EPAN at the platform level**: add a `FEAT_EPAN` extension and
   change `CHAOS/gem5/src/arch/arm/regs/misc.cc:5813` to advertise
   `ID_AA64MMFR1_EL1.PAN = 3` when it is present, e.g.
   `mmfr1_el1.pan = release->has(FEAT_EPAN) ? 0x3 :
   (release->has(FEAT_PAN) ? 0x1 : 0x0);`, and add the extension to the
   release lists in `ArmSystem.py`. Agent B is the sole `src/arch/arm`
   writer, so Agent C did not touch this. Then rebuild, re-freeze the binary
   SHA, and rerun the full audit. gem5's AP model already produces the
   correct EL0 read-deny / fetch-allow behavior for `AP=0b10`, but EPAN's
   effect on privileged PAN semantics (`mmu.cc` PAN checks use `FEAT_PAN`)
   must be reviewed before advertising it.
2. **Redefine R03** (researcher decision). There is no faithful userland
   alternative without EPAN: an EL0 *data* permission denial on a *valid,
   executable* leaf is precisely what EPAN enables; PROT_NONE is a
   translation fault and duplicates no frozen context faithfully.

Recommendation: run the R03 control as a diagnostic anyway to capture the
real `pte_value` (AP=0b11) and the `NO_ELIGIBLE_EVENT` result as the formal
blocker evidence, then mark R03 BLOCKED pending a platform decision.

### 6.2 R03 wording risk: AP=00 vs AP=0b10

The approved text says AP=00. The real kernel `PAGE_EXECONLY` constant is
`0x0020000000000f83` → `AP[2:1]=0b10`. Both deny EL0 read/write in gem5;
the gate must accept 0b10 as the expected value and reject 0b01/0b11. If the
authority text insists on AP=00, an otherwise-correct EPAN pilot would be
falsely marked BLOCKED.

### 6.3 R05 PTE proof may only show the populate walk

In the old R04B trace, `mprotect(PROT_READ)` invalidated the TLB
(`tlbi_issue`/`tlbi_invalidate`) but no new `pte_decode` appeared before the
fault; the cached entry already had `UXN=1` (the RW populate PTE was
`0x68000083577fc3`, UXN=1). R05's denial is still by XN, but the pilot report
must quote the actual `pte_decode` it has (and say which walk it is) rather
than claim a post-mprotect walk if none exists. The populate PTE is
sufficient to prove UXN=1; the kernel constant `protection_map[9]
= 0x0060000000000fc3` (AP=0b11, UXN=1) independently proves the final
`PROT_READ` mapping is XN.
