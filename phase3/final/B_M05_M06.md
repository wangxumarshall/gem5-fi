   Execute-mode fetch lookups have no `Request` inst seq. `MMU::getTE` now

### 1.3 Why this cannot alter translation/fault results

* The synthetic id is created only when **all** of: `!req->hasInstSeqNum()`,
  `mode == Execute`, `mmuTraceEnabled()` (`write_log && mmu_trace`) and
  `mmuTraceVa(vaddr)` (the `--prop_mmu_va_lo/hi` window). Any other request
  sees `chaos_synthetic_seq == 0`, exactly today's behaviour.
* The id is written **only** to `TLB::chaosLookupSyntheticSeq` and
  `CHAOSPropagation`'s transaction map. All fault-model gates
  (`mmuTargetSeqMatch`, M01/M02 lineage, M03/M04/M05/M06/M07 activation,
  CHAOSArmTLB correlation) read `chaosLookupReqSeq`, which for fetch stays
  **0**. In particular the M05 activation in `table_walker.cc:2954` still
  derives `seq` from `req->hasInstSeqNum()` (0) and its eligibility gate
  `mmuTargetSeqMatch(0)` is unchanged.
* `Request` objects, `TlbEntry` payloads, permission results and returned
  fault objects are never touched. The synthetic id is trace metadata only.
* Real-seq (data) requests take the `chaosLookupReqSeq != 0` branch of
  `chaos_trace_seq`, i.e. the identical value and identical code path as
  before; the emitter fallbacks are guarded by `!seq` and therefore never
  execute for a data request.

### 1.4 Collision and determinism guarantee

Synthetic ids start at `2^63` and increase by one per minted identity
(`2^63+1, 2^63+2, …`), deterministic in simulation order. `mmuBeginTxn`
refuses any value `>= 2^63` that is not in `mmu_synthetic_seqs`, so a real
`DynInst::seqNum` that ever reached the reserved range would be dropped from
the trace instead of aliased. `UINT64_MAX` stops allocation. No fetch
translation is ever assigned another fetch's id, and real dynamic sequences
are `< 2^63` in any run this repository can execute (the counter would need
~9.2e18 instructions to reach the namespace).

`translation_start` (with `dyn_inst_seq_kind=synthetic_execute_fetch`),
`tlb_lookup_miss` on `itb`/`l2_shared` (same marker), `ptw_start`,
`pte_read`, `pte_decode`, `partial_entry_insert`, `tlb_fill`,
`tlb_entry_insert` **with the fault id** (the walker's insert context now
carries the synthetic tid, and `mmuFaultActivate` stamps its `fault_ptag`),
`translation_result`, `lsu_request` (`mode=Execute`). The existing
`mmu_fault_activate` also gains a non-zero `translation_id`. Read/fill/insert

through the exact walker transaction id (`setChaosMmuContext`), but the

(no seq), so they use the open synthetic transaction for the VA. If two
fetch translations of the *same* VA are pending concurrently, the result of
the older one could attach to the newer still-open transaction. It cannot
change a result or a fault; it only affects which synthetic id a result row
names. For the M05 R05 fault chain the authoritative rows are the
walk/fill/insert events, which are exact.

### 2.2 Is the corrupted descriptor used by an architectural walk?

* **R01/R02: yes.** The faulted dynamic instruction's own walk decodes the
  cleared descriptor, `generateLongDescFault` produces the `TranslationLL`
  Data abort, it is delivered to EL1, the instruction is squashed, the
  kernel resolves the spurious fault, and a retry (new dyn seq, e.g.
  `206164169` at pc `0x400b60` in R01B) reads the untouched in-memory PTE
  and commits. The corruption exists only in the walker's local copy; the
  PTE in memory is unchanged.
* **R03/R04/R05: no.** The faulted instruction was squashed at ev 4410
  (before the L3 decode at 4427/4428). The walker nevertheless finished the
  walk and consumed the local descriptor, but the walk belonged to a dead
  instruction. Later dynamic instructions to the same VA re-walk from the
  clean page table, fill the TLB with the correct PFN (`0x834b6`), and the
  eventual architectural access hits that clean entry (or a later warm hit
  that is untraced because warm hits create no transaction). No exception
  is delivered and the guest reads its own correct sentinel
  (`observed==sentinel`, W10 `result=PASS`).

The cross-run `control_oracle.diff=true` (faulted `observed=0x63` vs control
`0x7d`) is an **artifact**: W10's sentinel is `0x5A ^ (target_index & 0xFF)`
computed from the per-run chosen PFN pair, so the sentinel byte differs
between runs. It is not corruption and must not be read as SDC evidence.
