## M07 — Permission Grant Decision Inversion

### Where the decision actually happens (source map)
- `mmu.cc:2115-2118` (S1) and `mmu.cc:2096-2100` (S2): `checkPermissions64` is called only
  when `isCompleteTranslation(te) && fault == NoFault`. A walker fault returns earlier
  (`mmu.cc:2071-2078`), so no permission evaluation happens.
- Grant computation: `mmu.cc:716-724` -> `s1PermBits64` (`mmu.cc:1089-1122`) ->
  `s1DirectPermBits64` (`mmu.cc:1013-1086`). AP=00 gives ur=uw=0; XN gives ux=0;
  `req->isAtomic()` selects `grant_read && grant_write`; a store-conditional is **not**
  `isAtomic()` (it is `Request::LLSC`, `str64.isa:88`).
- Denial branch: `mmu.cc:793-815` produces `DataAbort`/`PrefetchAbort` with
  `ArmFault::PermissionLL + lookupLevel`.
- Walker-side faults (LPAE): `table_walker.cc:2266-2275` Invalid -> `TranslationLL`;
  `table_walker.cc:2290-2303` af()==0 -> `AccessFlagLL`, both via
  `generateLongDescFault` (`table_walker.cc:2079-2089`). XN is **not** a walker fault.
- Therefore one post-walk authorization site covers Read/Write/Execute/Atomic; walker
  faults (translation/address-size/access-flag) precede it and are outside it.

### R02 — atomic RMW store denial
- `objdump workloads/mmu/W14/mmu_w14`: `0x400fec ldxr x1,[x0]`, `0x400ff4 stxr w3,x2,[x0]`.
- Trace: LDXR ev288 `permission_eval mode=Read grant`, ev289 `translation_result pc=400fec`,
  LDXR commit ev301. No event at all carries `pc=400ff4`, no Write translation, no second
  `permission_eval`.
- The STXR request is store-side `BaseMMU::Write` (`lsq.cc:1329-1330`) and `Request::LLSC`.
  It hits the DTLB warmed by the LDXR, so no miss-txn exists; `mmuNotePermission`
  returns early when `mmuTxnForSeqVa()` is 0 (`CHAOSPropagation.cc:3798-3804`). That is why
  the deny is invisible, not because the deny is elsewhere.
- The deny itself is real and at `mmu.cc:809-813`: run terminal gives
  `signal=11 si_code=2 (SEGV_ACCERR) fault_addr=0x400d000000 shared_changed=0` on a
  valid PROT_READ PTE (AP=0b11 -> grant_write=0). `handleLockedWrite`
  (`lsq_unit.cc:1111`, `isa.cc:1966-1984`) runs after `buildPackets()`; it is not the
  fault source.
- The M07 hook *is* reached, but `m07_mode` is `"Write"` (`mmu.cc:748-749`, because
  `is_atomic` is false) while the manifest target is `"Atomic"` -> key mismatch ->
  `mmu_fault_unactivated` (`fault_reason=no_eligible_target_event`).
- Do not "fix" this by setting `--mmu_target_mode Write`: R01 and R02 share VA
  `0x400d000000`, and R01's plain store would win eligible index 1.

### R03 — PROT_NONE read
- Trace `TEST-M07-R03`: ev263 and ev272 `pte_decode walk_level=L1 pte_address=0x81c1f800
  pte_value_before/after=0 descriptor_type=Invalid`; independent
  `TEST-M07-P3B-R01` and `TEST-M07-P3B-CTRL-R01` reproduce the same 0/Invalid L1 walk.
- Therefore the walker takes `LongDescriptor::Invalid` -> `TranslationLL` L1
  (`table_walker.cc:2266-2274`) and `checkPermissions64` is never called. There is no
  AP=00/AF=0 permission decision in this run; the run's `si_code=2` comes from the kernel
  classifying a fault on a PROT_NONE VMA, not from a hardware permission fault.
- This is not just the un-populated mmap: arm64 `PAGE_NONE` clears `PTE_VALID`
  (`/usr/src/kernels/5.10.../arch/arm64/include/asm/pgtable-prot.h:84`, same encoding family
  as the 5.15.36 guest). Populate-then-`mprotect(PROT_NONE)` still yields descriptor bits
  [1:0]=0b10, and gem5 `LongDescriptor::type()` decodes 0b10 as Invalid
  (`table_walker.hh:530-560`). **R03 cannot be M07 with PROT_NONE.**
- Valid-descriptor alternative that *is* the same model: execute-only mapping. The guest
  config extracted from `gem5-fs/vmlinux` has `CONFIG_ARM64_EPAN=y`; `PAGE_EXECONLY` has
  PTE_VALID=1 and PTE_USER=0 (AP=00), so an EL0 load is denied inside
  `checkPermissions64` (`s1DirectPermBits64`, ap=0b00 -> ur=0). Requires only a workload
  change (Agent C), not a new hook.

### R05 — PROT_NONE fetch
- `TEST-M07-R05` ev263: `pte_decode walk_level=L1 pte_value=0 Invalid` for `0x400d600000`.
  Same translation-fault argument as R03. XN never reaches the walker; the valid-XN case is
  exactly R04 (activation ev268 mode=Execute, verdict COMPLETE/SDC).
- **R05 as a PROT_NONE fetch is impossible under M07**; it duplicates R04's XN denial.

### Same-model statement (explicit)
- R02 needs no new hook: the denial already occurs at `checkPermissions64`
  (`mmu.cc:809-813`). Fixing the correlation label (`LLSC && Write` -> `Atomic`) and
  observing the deny is the **same** logical model: one invertible grant decision, one
  one-shot injection, PA/permissions otherwise untouched.
- R03/R05 cannot use a "walker-side AP/XN grant inversion": with an Invalid descriptor
  there is no AP/XN grant to invert. Inverting it would require fabricating a valid
  translation (invented PFN) — that is a different model (M05/M06 fabricated-translation
  family), and must not be labelled M07.

## M08 — Final PA Materialization Corruption

### Path
`mmu.cc:1281-1328`: after `testAndFinalize` returns NoFault, key+seq match -> PA xor
(`mmuM08PaXorMask`, 4096) in the PA domain -> one-shot `mmuFaultActivate("M08",
"mmu_translate_set_paddr", 0, seq, ...)` -> `req->setPaddr(new_pa)`. Only the Request PA
changes; `te` is read-only. Config in all three runs: `mmuTargetSeq=0`,
`mmuEligibleEventIndex=1`, so the FIRST VA/key-matching translation activates.

### Per-run root cause (activation burns on a squashed instruction)
- R02: activation ev4361 seq99901600 tid2. Earlier real squash ev4338 seq99901600
  (tick 264455706240 vs activation 264455861751). Chain after activation: ev4362
  translation_result, ev4363 lsu_request, then nothing; summary ev4551 `consumed=0`
  `activated_not_consumed`. Consuming load is seq99901648 (tid3, ev4339 miss ->
  cache_response ev4375, memory_response ev4377, rf_writeback ev4378, commit ev4379,
  pc400d30).
- R03: activation ev4421 seq101162556 tid4. Squashes ev4393 (101162556) and ev4398
  (101162604) precede it. Live instruction seq101162645 (tid6) commits ev4440.
- R04: activation ev4478 seq102416403 tid7. Squashes ev4454 (102416403) and ev4464
  (102416444) precede it; the second lookup then hits ev4481 but the instruction is
  already dead. The real (third) dynamic load is a warm TLB hit with no miss-txn, hence
  untraced; the same run's W10 line still proves R04's load executed
  (`ctx=R04 ... observed=0x7d ... result=PASS`).
- Common: the one-shot latch (`CHAOSPropagation.cc:4520-4524`) then rejects every later
  translation of the same VA; the injected chain stops at `lsu_request`.

### Proposed gate (minimal, same fault site and semantics)
Use the squash witness already recorded at `CHAOSPropagation.cc:4118-4148`
(`mmu_txn[tid].squash_event`, field at `CHAOSPropagation.hh:1576`, seq->tid map at
`hh:1582`) and add:
```cpp
bool CHAOSPropagation::mmuSeqSquashed(uint64_t seq) const {
    if (!seq) return false;
    const auto sit = mmu_seq_txn.find(seq);
    if (sit == mmu_seq_txn.end()) return false;
    const auto tit = mmu_txn.find(sit->second);
    return tit != mmu_txn.end() && tit->second.squash_event != 0;
}
```
and in `mmu.cc:1292` (before `mmuEligibleEvent(8)`, so dead translations do not consume
the ordinal):
```cpp
if (pa_prop->mmuTargetSeqMatch(pa_seq) &&
        !pa_prop->mmuSeqSquashed(pa_seq) &&
        pa_prop->mmuTargetKeyMatch(...)) { ... }
```
For robustness independent of `--prop_mmu_trace`, also insert
`mmu_squashed_seqs.insert(inst->seqNum)` in `mmuNoteSquash` before its tracing
early-return (`CHAOSPropagation.cc:4113`) and query that set.

### Options quantified (evidence)
- eligible ordinal 2 (config only): dead pre-translations per target VA are R02=1,
  R03=2 (101162556, 101162604), R04=2; the live index is 2/3/3 -> no fixed index works.
  Reject.
- require inst seq + not prefetch + not speculative: all three bad activations have
  seq!=0 and are non-prefetch Reads; `Request` has no speculative bit -> suppresses 0/3.
  No-op.
- require TLB hit (no walk): would suppress R01's cold-walk activation ev4311 (which then
  commits and is the current SDC anchor). Reject.
- commit/writeback evidence: only known after issue; acting on it moves the corruption to
  the LSQ/commit, changing the fault site. Reject.
- squash gate: suppresses 3/3 dead activations; keeps R01 (seq98623352 has no squash) and
  R05B (seq230757518 has no squash). Expected R02/R03 activation on seq99901648 /
  seq101162645 with full commit chains; R04 expected to activate on the warm-hit third
  instance (source: `mmuFaultActivate` creates a consumer txn when none exists, and
  `mmuBeginTxn` inserts the seq into `mmu_traced_seqs`, `CHAOSPropagation.cc:3126-3127`).
  Must be confirmed by rerun; R04's third instance is inferred, not observed.

### Risks
- Race: the gate depends on the LSQ squash (`lsq_unit.cc:1204-1208/1283-1287`) being
  recorded before walk completion. Observed margins are large (R02 155511 ticks, R03
  146254, R04 158158/81988) but this is not a hard guarantee.
- The txn-witness variant requires tracing; prefer the unconditional set.
- Retract-and-rearm of the one-shot when the origin later squashes was rejected: it would
  break "one formal injection / one fault id" and need validator support.
