group-by 验证很漂亮，6/31 ≈ 18.7% 的解释成立，x1/x4/x6/x8 的集中就是 A1' 的预告片。
但表里有个红旗你没看出来，那 4 个异常比你判断的严重得多。

【★ 不是 0.4% 残留，是 57% 失败率】
看 x1 那一行：
    arch_reg  n   reads>0  SDC  total_reads
    x1        7   3        7    3            ← SDC(7) > reads>0(3)
    x4        5   5        5    3,311,339
    x6        8   8        4    292,186

x1 上 4/7 = 57% 的注入被计数器漏掉，不是 4/1000 = 0.4%。

而且 total_reads 是决定性的红旗：
x1 是 sum += a[i] 的累加器，【每一轮迭代都被读】，它的每个版本被读恰好 1 次
（读完就被新版本取代）。7 次注入应该是 total_reads = 7，实测【3】。
对比数据指针 x4 有 330 万次读。
★ 计数器在这个负载里最重要的那个寄存器上，一半的时候完全失灵。

【这让闭合结论比看起来弱得多】
SDC | reads==0 的分母里，绝大多数是【真正的死寄存器】——
它们 reads==0 是因为真的没人读，这些格子【不构成对计数器的检验】。
唯一真正检验计数器的场景是"热寄存器 + reads==0"，
而那恰好是它失败的地方。
所以这个闭合是"数值上成立，但在唯一能证伪它的地方失效"。不能这么写进报告。

【为什么不能带病走】
reads_before_overwrite 是 P2/P3 的地基字段：
ILP sweep 要用它解释三层差异，A1' 要用它做"存活窗口 vs SDC 率"的相关性分析。
如果它在热寄存器上系统性漏计，而热寄存器恰好是产生 SDC 的那批，
所有基于它的分析都会是【反的】—— 你会得出"SDC 主要来自没被读的寄存器"
这种荒谬结论。跑完 BM2、BM3 再发现，就是三轮数据重来。

【★ 停止猜测，做定向 dump（1-2 小时，不是半天）】
你已经猜了两轮（getWritableReg？别的路径？）。不要再猜。

挑一次 x1 的注入（比如 p257），在注入之后的 5000 个周期里，
【把对该物理寄存器编号的每一次访问都打出来】：
    周期号 | 读还是写 | 哪条指令（seqNum + PC）| 值
然后拿这份原始日志跟计数器报的数对。
这直接给出"计数器漏掉了哪一次访问"，不用推理。

【一个具体的怀疑方向，供你验证时参考】
gem5 O3 在 execute 阶段读源操作数，但【旁路/前递路径】可能让消费指令
直接从产生指令的输出拿值，不经过 PhysRegFile::getReg。
累加器这种紧邻依赖（上一轮的 sum 立刻被下一轮读）
【正好是最容易走前递、最不容易经过寄存器堆的】——
这能同时解释"为什么偏偏是 x1"和"为什么是一半"。

★ 如果确认是前递，结论要改成：
  reads_before_overwrite 测的是【经寄存器堆的读】，不含前递。
  这是个必须写进 threats to validity 的重要限定，
  而且它对"注入值怎么传播"的理解有实质影响 ——
  它意味着一部分 SDC 是通过前递网络传播的，压根不经过寄存器堆。

【顺序】
1. 定向 dump 查清 x1 的漏计根因（限时 2 小时）
2. 根据结果决定：
   - 能补上漏的读 → 补，重跑 BM1 n=1000

     在文档里写清它不含前递，然后继续
3. 之后才做：补 BM1 配对 500 → SHA-256

【新主线：两种 RAT 故障，都是持久模型】
======================================================================

不做"单次查表出错"。只做持久损坏 —— 一次触发，后果持续。

■ 注入 A：RAT 表项损坏（建模 RAT 存储单元的比特翻转）

  X17 的表项本来是 P50，被改成 P77。

  后果链：
    - 指令正常写到 P50（它拿到的目的标签是对的）
    - 但表里记的是 P77
    - 后续读 X17 的指令拿到 P77 → 读到【别人的变量的合法值】
    - P50 成为孤儿，永不释放（leak）
    - X17 下次重命名时，rename 认为 prev = P77 → 错误释放 P77（duplication）
      而 P77 的真正主人还在用它

  ★ 这一个就覆盖了"源映射错"的全部效果 ——
    在持久模型下，源侧和目的侧不是两次注入，是同一次注入的两个后果。

  预期：读到另一个活跃变量的合法值 → 【纯 SDC 为主】

■ 注入 B：目的标签损坏（建模分配结果送往执行单元途中出错）

  rename 分配了 P50，表里正确记录 X17 → P50，
  但指令拿到的目的标签是 P77。

  后果链：
    - 指令把结果写进 P77，把 P77 真正主人（比如 X20）的值冲掉
    - P50 从没被写过
    - 后续读 X17 的指令读 P50 → 读到未初始化 / 过期内容

  预期：双重污染（写错人 + 自己丢）→ 【crash 和分配器不一致比例更高】

■ 两者的不对称正是要测的
  A = "读错人"          → 预期纯 SDC 为主
  B = "写错人 + 自己丢"  → 预期 crash 为主

======================================================================
【实现关键】
======================================================================

■ ★ 绝对不要翻指针
gem5 的 RAT 存的是 PhysRegIdPtr（= PhysRegId*，宿主机 64 位指针，
指向 regfile 里的 std::vector<PhysRegId>）。直接对它做 bit-flip 必崩，
那不是故障注入，是仿真器挂了。

正确做法：
  1. 拿到目标物理寄存器的【索引】（不是指针）
  2. 对索引做 bit-flip
  3. 检查新索引是否在 [0, numPhysIntRegs-1] 内
     ★ 越界的要【单独记一类】，不要丢弃也不要 clamp ——
       真实硬件上索引越界会指向不存在的存储，是一种独立的失效模式，
       但 gem5 里会直接崩，所以记录后跳过该次注入并单独统计比例
  4. 从 regfile 的 intRegIds 数组按新索引取出【合法的】PhysRegIdPtr
  5. 用它替换表项 / 目的标签

■ 两种注入的触发时机不一样，这一点很关键

□ 注入 A（表项损坏）：可以在任意周期直接改表
  真实的存储单元翻转不需要等 rename 来访问它。
  所以：到达注入周期 → 直接调 setEntry(X17, 损坏后的 PhysRegIdPtr)。
  不需要拦截 rename 流程。

□ 注入 B（目的标签损坏）：必须等到目标架构寄存器【被作为目的寄存器重命名】
  目的标签只在 rename 一条写 X17 的指令时才存在。
  所以：到达注入周期后【等待】X17 的下一次目的重命名，在那一刻篡改
  送给指令的物理寄存器标签，但【不改表项】。
  ★ 要记录实际触发的周期（可能晚于请求的注入周期）。
  ★ 如果程序结束前 X17 从未被作为目的重命名 → 记为 Inactive，
    不要算进分母。

■ 挂钩点（gem5 v25，你自己读源码确认）
  src/cpu/o3/rename_map.hh
    SimpleRenameMap::lookup(RegId)      → PhysRegIdPtr
    SimpleRenameMap::rename(RegId)      → RenameInfo{新, 旧}
    SimpleRenameMap::setEntry(RegId, PhysRegIdPtr)
    UnifiedRenameMap                     按寄存器类分发的包装
  src/cpu/o3/rename.cc
    Rename::renameSrcRegs()              源映射的调用点
    Rename::renameDestRegs()             目的映射的调用点，
                                         inst->renamedDestIdx(...) 在这里

  注入 A 建议直接用 UnifiedRenameMap::setEntry()。
  注入 B 建议挂在 Rename::renameDestRegs() 里 inst->renamedDestIdx() 那一行。

  ★ 但你读完源码后自己判断，如果有更合适的位置，告诉我理由，我确认后再动手。

======================================================================
【★ 一个绕不开的麻烦：分配器会跟着坏】
======================================================================

把 X17 的映射改到 P77，而 P77 当前是 X20 的。之后：
  X17 被重新写 → rename 认为要释放 P77 → 但 X20 还在用它
  → 物理寄存器重复分配 / 提前释放 → 【gem5 的 assert 会炸】

这在真实硬件上是【物理正确】的行为 —— RAT 坏了本来就会引发分配器错乱。
IDLD（MICRO 2022）研究的 leakage / duplication 正是这个机制。
但在 gem5 里它会表现为 assert 失败，而不是一个有意义的程序级结果。

★ 分类口径提前定死：
  这类崩溃算 Crash 的一个【子类】，单独标记 rename-inconsistency，
  因为它确实是这类故障的真实后果之一，不是我们的 bug。

★ 但必须和"注入代码本身写错导致的崩溃"严格分开。
  ★★ 请在实现前先告诉我你打算怎么区分这两者。
     我的建议方向：在注入器里维护一个"预期会引发不一致"的标记 ——
     注入时就知道 corrupted_phys_idx 当前有没有主人，有主人就预期会不一致；
     然后按 assert 的位置和消息文本二次确认。
     但你有更好的办法就用你的。

【分类口径】
======================================================================

  Masked                  exit 0 且 stdout 与黄金完全一致
  SDC                     exit 0 但 stdout 与黄金不同        ← 唯一真正关心的
  Crash                   非零退出码 / 收到信号；

  1. 绝对不能把 Hang / Crash 归到 SDC
  2. Inactive 和 OutOfRange 都不计入主分母，但要报比例
  3. tool-bug 单独一类，绝不混进 Crash
