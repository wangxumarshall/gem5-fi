选方案 2：现在就补 maxFaults 补丁。

【补丁要求】
1. CHAOSReg 加 maxFaults 参数（UInt64，默认 0 = 不限制，保持向后兼容）
2. 加计数器，注入次数达到 maxFaults 后不再 scheduleAttackEvent
3. ★ 同时把 lastClock 的语义在代码注释里写清楚（README 与实现不符那两点），
   并在 CHAOSReg.py 的参数描述里改正
4. 重编译只需要 CHAOSReg.o + 链接

【补丁的验收】
maxFaults=1 时，stats 里 numFaultsInjected 必须严格 == 1，不能是 2。

【★ 检查 2 的验收方式要改 —— 这一条很重要】
单个比特翻转【大概率会被 masked】。按 ITC'23 的 ARM 数据，整数寄存器的
SDC 率只有 0-6.9%，加上崩溃和挂死也就三成左右。
所以【不能按"跑一次就要看到偏离"来验收】—— 那样你会误判成"注入没生效"，
然后去改本来没问题的代码。

正确做法：跑 30-50 次单次注入，每次在 ROI 内随机采样一个注入周期
（ROI 大约是 numCycles=3,673,507 的范围，注意跳过前面的 libc 初始化阶段，
你自己判断跳多少合适并说明依据）。验收标准是：
  a) 每一次 numFaultsInjected == 1        ← 补丁的验收
  b) fault_injections.log 每次都有且只有一条记录
  c) 【至少有几次】行为偏离黄金             ← 机制能传播的证据
  d) 大部分被 masked 是【正常的、预期的】，不是 bug

同时也跑一组 probability=1.0 的多次注入作为粗对照（几次就够），
证明机制在高强度下必然产生偏离。

【顺带】
这 30-50 次的结果直接拿来做检查 3 的分类器输入，两步可以合并。

【配置纪律】
补了 maxFaults 之后，注入次数一律用 maxFaults 控制，
lastClock 统一设 0（不限制），不要再用 lastClock 做窗口控制 ——
避免踩你自己发现的那个静默零注入陷阱。
