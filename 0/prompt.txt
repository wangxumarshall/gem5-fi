【第一步：写 ARM O3 配置脚本】
======================================================================
目标平台是华为鲲鹏 920 的 TaiShan v110 核。用 gem5 的 ARM O3CPU，SE 模式，
按下面这组参数配置：

  流水线宽度（fetch/decode/rename/dispatch/issue/wb/commit 全部）: 4
  numROBEntries        : 97
  numPhysIntRegs       : 125     （93 推测 + 32 已退休）
  numPhysFloatRegs     : 96      （64 + 32）
  numPhysVecRegs       : 96      （NEON 用）
  LQEntries            : 65
  SQEntries            : 47
  numIQEntries         : 64      （未实测，先用这个值，后续标定）

  执行单元（用 FUPool 配）:
    整数 ALU × 3（通用）+ 1（多周期专用，乘除）
    FPU/SIMD × 2 个端口，FP32 FMA 延迟 5 周期
    AGU × 2（MemRead / MemWrite）

  缓存:
    L1I 64KB
    L1D 64KB 4 路，命中 load-to-use 4 周期
    L2 512KB 私有

★★ 两个必须遵守的约束 ★★
  1. 【不要配 SVE】鲲鹏 920 只有 128-bit NEON，没有 SVE。
     gem5 支持 FEAT_SVE/SVE2，但配上会偏离目标机器。保持默认不启用。
  2. 【LQ/SQ 的疑点要在注释里标注】
     LQ 65 + SQ 47 = 112 > ROB 97。物理上在飞指令不应超过 ROB 容量，
     这个数可能包含了退休后仍在排空的 store buffer 表项，或是微基准测量偏差。
     先照配，但在配置文件里写注释标明这个疑点，后续我们会用微基准复核。

配置风格你自己判断：CHAOS 的 examples 是老式 configs 风格（system = System() 那种），
gem5 v25 也有新的标准库（gem5.components）。选一个能跟 CHAOS 正常配合的。
如果用新标准库跟 CHAOS 的 SimObject 挂载方式冲突，就用老式风格。

--- 检查 1：建立黄金参考 ---
不启用任何注入，跑基线。
记录：退出码、完整 stdout、m5out/stats.txt 里的关键指标（simInsts、simTicks、
numCycles）。存成文件（比如 golden/baseline.txt）。
★ 连跑三次，确认三次完全一致。gem5 是确定性的，如果三次结果不同说明配置有问题，
  停下来排查。

--- 检查 2：证明注入真的生效 ---
同一个配置，加上 CHAOSReg：
    fault_injector = CHAOSReg(
        cpu = system.cpu,
        probability = 1.0,          # 拉满，每个检查点都注
        faultType = 'bit_flip',
        bitsToChange = 1,
        regTargetClass = 'integer',
        writeLog = True
    )
    system.CHAOSReg = fault_injector
（参数名以 CHAOSReg.py 源码为准，如果和我写的不一致，以源码为准并告诉我。）

必须同时满足三条：
  a) 生成了 fault_injections.log 且里面有内容
     （README 说格式是 "Cycle, Register, Mask, FaultType"）
  b) stats.txt 里 system.CHAOSReg.numFaultsInjected > 0
  c) ★ 程序行为跟黄金参考【不一样】（崩了、挂了、输出错了，任何一种都行）

★★ 如果 (c) 不满足 —— 注了一堆但程序照常跑完、输出完全一致 ——
   【停下来排查，不要继续】。可能的原因：
     - 注入的寄存器从未被读过
     - 注入时刻落在程序 ROI 之外（比如都在 libc 初始化阶段）
     - 注入后立刻被下一次写入覆盖
   请把 log 里注入的寄存器编号和周期打印出来，帮我分析。

--- 检查 3：分类器验收 ---
写一个 Python 脚本，输入一次运行的产物（stdout、退出码、stats.txt），
输出五分类之一：

  Masked   : 退出码 0 且 stdout 与黄金完全一致
  SDC      : 退出码 0 但 stdout 与黄金不同        ← 唯一真正关心的
  Crash    : 非零退出码 / 收到信号
  Hang     : 超时（阈值 = 黄金运行 wall-clock 时长 × 3）
  未激活   : stats 里 numFaultsInjected == 0

★★ 三条硬性纪律，必须在代码里体现 ★★
  1. 绝对不能把 Hang 和 Crash 归到 SDC
  2. "未激活"要单独统计，不能算进分母（否则脆弱度会被系统性低估）
  3. gem5 自己 panic / assert 失败要【单独一类】，不要混进上面任何一类
     （那是注入越界，是我们工具的 bug，不是被测系统的行为）

验收方法：手工构造这五种情况各一次（可以通过调 probability、改注入目标、
故意设很短的超时来构造），确认脚本每种都分对了。
把五个测试用例和脚本的判定结果都贴给我看。
