【一、我的预测错了，你的解释是对的】
======================================================================
我说 layer2（已分配但不在 renameMap）应该 ≈ 0，理由是"被取代 = 没有未来读者"。
这个推理是错的。

"被取代"只意味着之后新 rename 的指令不再指向它，但
【已经 rename、还没执行的指令仍然握着它】，而它要等覆盖它的那条指令
【提交】才会被释放回 free list。所以"被取代"和"没人读"之间隔着一整个执行窗口。

  指令 A 写 X17 → 分到 P50
  指令 B 读 X17 → rename 时记下"读 P50"
  指令 C 写 X17 → 分到 P77，renameMap[X17] 改指 P77，P50 变成"被取代"
                  但 B 还没执行，它手里还是 P50
                  B 执行时读 P50 → 读到注入值 → SDC
  P50 要等 C 提交才释放

★ 所以 layer2 的 5.7% 不是"未闭合的残留"，而是一个
  【被正确识别出来的额外机制】。表述要改过来，不要写成"有残留没解释"。

正确的划分标准不是"在不在 renameMap"，而是【有没有待执行的读者】：

  层                   有哪种读者                      预期    实测
  free list            两种都没有                      0       0/9      ✓
  已分配·被取代         只有"已 rename 未执行"的读者     中等    5.7%     ✓
  在 renameMap         "已 rename 的" + "未来才 rename 的"  最高    9.8%     ✓

layer3 > layer2 > layer1 = 0，序是对的，机制清楚。故事是闭合的。

【五、BM 阶段的任务】
======================================================================

■ 目标
准备一组 benchmark，覆盖不同的 ILP 和寄存器压力，
把之前拿到的两个【单点数字】变成【随 ILP 变化的曲线】：

  单点 1：commit vs frontend 的分裂率 17.5%、低估倍数 1.2x（低 ILP 下测的）
  单点 2：arch vs phys 的 SDC gap 1.84x（同一个负载下测的）

这两个都应该是 ILP 的函数，不是常数。曲线比单点有说服力得多。

■ 先做 3 个跑通（AES、矩阵乘等第一批曲线出来再补）

  1. 现有的 累加 + CRC32 微基准         —— 已有，作为基线
  2. SHA-256                          —— 依赖链长、低 ILP、"每一位都重要"
  3. 一个 MiBench 程序（你选一个合适的）—— 学术界标准负载，横向可比

  期望这三个覆盖不同的 ILP 区间。如果实测下来 IPC 太接近，
  再加一个高 ILP 的（比如小规模稠密矩阵乘，独立乘加多、依赖链短）
  和一个极低 ILP 的（指针追逐）。

■ 编译要求
  ★ 本机就是 aarch64，用系统 gcc 原生编译，不需要交叉工具链
  ★ 必须静态链接：gcc -static -O2 -o <name> <name>.c
    （gem5 SE 模式对动态链接支持有限）

■ 每个 benchmark 的准备工作
  1. 确认在 gem5 ARM SE 模式下能正常跑完
  2. 调整输入规模，让 wall clock 落在 20-40 秒
     ★ 缩规模时不要删掉计算核心，只缩循环次数或数据量
  3. 建黄金参考：不注入，连跑三次，要求逐字节一致
     （gem5 是确定性的，三次不一致说明配置有问题，停下来查）
  4. 存成 golden/<benchmark>.txt，记录：
     stdout、exit code、simInsts、simTicks、numCycles、wall clock

■ ★ 每个 benchmark 还要额外记录这些指标（ILP sweep 的横轴和解释变量）
  - IPC = simInsts / numCycles                    ← sweep 的主横轴
  - free list 平均大小（采样若干时刻取平均）
  - rename 阶段 Blocked/Unblocking 占周期比例      ← 寄存器压力指标
  - 三层分布：free / 已分配被取代 / 在 renameMap 各占多少
  这四个指标本身就是一张表，能解释后面 SDC 率的差异从哪来。

■ 每个 benchmark 要跑的注入
  三路 bit_flip，各 200 次：
    arch_commit    随机架构寄存器 [0,30]
    arch_frontend  随机架构寄存器 [0,30]
    phys           随机物理寄存器 [0, numPhysIntRegs-1]

  另外配对 40 对（同 seed / 同 cycle / 同架构寄存器 / 同掩码，
  跑 arch_commit 和 arch_frontend），用来测该 benchmark 的分裂率。

  参数：bitsToChange=1、maxFaults=1、lastClock=0、maxRegIdx=30
  注入周期：ROI 取 [20%, 80%] × numCycles，均匀随机采样
  种子固定，rng_seed 按 seed*1000003 + run_id + 1 派生

【七、结果分类口径与三条纪律（保持不变）】
======================================================================

  Masked      exit 0 且 stdout 与黄金完全一致
  SDC         exit 0 但 stdout 与黄金不同        ← 唯一真正关心的
  Crash       非零退出码 / 收到信号；
              或 gem5 panic 且 panic 文本是 faults.cc 的 page fault
  Hang        超时（该 benchmark 黄金 wall clock × 3）
  Inactive    numFaultsInjected == 0
  tool-bug    gem5 panic 且 panic 文本【不是】 page fault

★ 三条纪律：
  1. 绝对不能把 Hang 和 Crash 归到 SDC
  2. Inactive 不计入分母：denom = n - Inactive，SDC rate = SDC / denom
  3. tool-bug 单独一类，不混进任何其他类
