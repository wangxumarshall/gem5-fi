## 1. 摘要与置信度

开机 **1592 秒（26.5 分钟）**后，CPU179 上的内核线程 kworker/179:1 在空闲调度（newidle_balance → load_balance → find_busiest_group）路径中，执行 `__per_cpu_offset[]` 数组装载指令 `ldr x20, [x0, x25, sxtw #3]`（x25=50，读 CPU50 的槽，跨槽为调度域遍历正常行为），**装载返回值 x20 = 00ffffb810e4a240 被结构性腐化**：canonical 内核指针必有的顶段 0xffff 标签分裂为「顶段 00ff 半标签 + 次高段 ffb8 前缀」，且 percpu 偏移必有的 4K 页对齐低 12 位被注入 0x240。该坏值经两条纯正确指令（`add x27,x1,x20`、`ldr x23,[x27,#288]`，代数逐位闭合）传播为非法地址 00ffc7a7ac4a3a20，触发 L0 translation fault 致命 Oops。RAS/EDAC/GHES 全程零上报，无任何前兆日志。

**三级置信度**：
- 现象层（x20 装载返回结构化坏值 → 经闭合加法传播 → 致命缺页）：**【实锤】**——dmesg 寄存器 dump + mod 2^64 逐位代数闭合（algebra_out.txt 第一~三节）；真值对照缺失不影响此层（不变式被破坏本身即证明坏值）。
- 通路归属（CPU179 核内装载返回通路的 lane/选通错位，非内存/软件/一致性）：**【强推】**——形态结构化 + 不变式破坏 + 09-11 当日四案全在 CPU179（本案为当日第 3 案）+ RAS 零上报；但因本案无 vmcore，无法像谱系 10 案那样实测"内存真值完好"，故降一级。
- 物理位点（bypass/移位网络 vs RF 写口 vs L1D 出口锁存）：**【假设】**——软件不可分辨。

## 3. 指令级解剖

### 3.1 Code dump 五指令窗口反汇编（dmesg L2624）

```
f9400782   ldr  x2, [x28]                  // +0x128（上文，未参与致命链）
f879d814   ldr  x20, [x0, x25, sxtw #3]    // +0x130 ← __per_cpu_offset[x25] 装载（腐化点）
2a1903e0   orr  x0, wzr, w25               // +0x134（dump 时 x0=0x32，为后续循环所用）
8b14003b   add  x27, x1, x20               // +0x13c ← x27 = rq(cpu) 基址 + percpu 偏移
(f9409377) ldr  x23, [x27, #0x120]         // +0x140 ← 致命装载：读 rq->cfs.avg 等（offset 288）
```

注：括号内为 pc 处指令。x0 dump 值 0x32 与 x25=0x32 逐字吻合，证明执行流精确停留在 +0x140、且 w25/x0 此刻同持槽号 50——寄存器快照内部自洽。

### 3.2 x25=50 跨槽（CPU179 读 CPU50 的槽）——正常行为，非异常

`__per_cpu_offset[]` 装载的索引是**被考察 CPU** 的编号，非当前执行核编号。`find_busiest_group` 在负载均衡中遍历调度域内各组，逐一读 `__per_cpu_offset[cpu]` 换算各 CPU 的 `rq` 实例——CPU179 的内核线程读 CPU50 的 percpu 槽是调度器亿万次执行的标准动作（谱系 12 案的 w25/x25 分布 6~179 同理）。**跨槽本身无异常，异常仅在装载返回值。**

### 3.3 kworker/179:1 内核线程上下文——newidle_balance 路径

Call trace（L2613-2623）：`find_busiest_group ← load_balance ← newidle_balance ← pick_next_task_fair ← pick_next_task ← __schedule ← schedule ← worker_thread ← kthread ← ret_from_fork`。

这是 kworker/179:1（PID 1205，events 工作池）**自身即将睡眠**的路径：worker 发现没有更多工作 → `schedule()` → `newidle_balance()` 趁机做一次空闲均衡 → 均衡代码读 percpu 数据 → 装载被腐化。两点含义：(a) 崩溃点在纯内核上下文，与用户态负载无直接因果（排除"某用户进程触发坏页"类解释）；(b) newidle 路径在该核上每次空闲都可能执行——**开机 26 分钟内该指令在 CPU179 上已被执行海量次，其中恰好一次读错**，这与谱系"间歇性、低概率、无应力累积"的画像一致。Workqueue `0x0 (events)`（无具体 work 函数）进一步印证此刻是调度器自身行为而非某延迟工作项。

### 3.4 代数闭合（algebra_out.txt，mod 2^64，全部 True）

1. **x27 = x1 + x20**：`ffffc7ef9b6596c0 + 00ffffb810e4a240 = 00ffc7a7ac4a3900` ——逐位闭合。加法器与 x1/x20 两个源操作数的读出**全部正确**；x27 的非法形态 100% 继承自 x20。逐 16 位段进位链亦闭合（[15:0] 96c0+a240→3900 进位 1；[63:48] ffff+00ff+1→00ff 进位 1，顶段自然回绕成 00ff——这正是 FAR 高段 00ff 的来源）。
2. **FAR = x27 + 0x120**：`00ffc7a7ac4a3900 + 0x120 = 00ffc7a7ac4a3a20` ——逐位闭合。AGU/寻址生成正确，fault 完全由坏 x27 决定。
3. **反证非移位偏移**：若误用 imm=0x48（未左移 3 位）则 x27+0x48=...3948 ≠ FAR，排除解码错误假设。

**结论**：致命链条上除 `ldr x20`（+0x130）这一条装载指令的返回值外，其余每一步（操作数装载、加法、地址生成）均被代数闭合证明正确执行。**腐化点唯一且收口于装载返回通路**——与谱系 12 案 §2.2 受害指令族唯一性完全一致（12/12 案中 11 案同一条指令）。

## 4. 形态分析：标签错位族——ff 标签跨段迁移的第 3 个独立样本

### 4.1 x20 = 00ffffb810e4a240 逐 16 位段解剖（algebra_out.txt 第四节）

| 段 | x20 值 | 真值（canonical percpu 偏移）应为 | 判定 |
|---|---|---|---|
| [63:48] | `00ff` | `ffff` | **半标签**：ff 保留在 bit47..40，bit63..48 为 00——标签整体下移一个字节 |
| [47:32] | `ffb8` | `c7xx` 之类随机段 | **主标签溢出段**：ff 前缀出现在 bit47..40 之后的 bit39..32 位置（ffb8 的 ff 恰好紧接顶段的 00ff，连起来是 `00 ff ff b8`——**原 0xffff 标签的两个 ff 字节都在，但整体右移了 8 位**） |
| [31:16] | `10e4` | 偏移随机位 | 数据段（无法直接判定真伪） |
| [15:0] | `a240` | **低 12 位恒 0x000**（percpu 偏移 4K 页对齐；谱系实测真值低 16 位有 e000/4000/8000 等，故不变式取低 12 位） | **页对齐不变式被破坏【实锤】** |

关键位级事实：把 x20 高 32 位排成字节串 `00 ff ff b8`，与真值标签 `ff ff xx xx` 对照——**ff ff 双字节标签完整保留、仅整体右移一个字节位置，尾部挤出一个 b8**。这不是随机位翻转（随机翻转不会恰好保留标签的全部 ff 字节），也不是存储坏位（那样每次读同地址都坏，谱系已证同槽复读正常），而是**字节/lane 粒度的位置错排**：数据内容大体健在，"哪个字节进哪个槽"错了。

### 4.2 跨 09-11 同日四连崩的标签迁移谱（algebra_out.txt 第五节；兄弟案数据仅取自各自 dmesg 原始 dump 行，未读任何报告正文）

| 案 | 转储时刻 | x20（坏值） | [63:48] | [47:32] | [31:16] | [15:0] | ff/ffff 沾染位置 |
|---|---|---|---|---|---|---|---|
| #22 | 09-11-14:31 | `9226e000ffffa4bd` | 9226 | e000 | **ffff** | a4bd | 完整 ffff 标签落在 [31:16]（下移 32 位） |
| #23 | 09-11-16:30 | `ffa9342267e000ff` | **ffa9** | 3422 | 67e0 | **00ff** | ff 前缀钉在 [63:56] + ff 尾缀落 [15:8]（双端沾染） |
| **#24** | **09-11-17:06** | **`00ffffb810e4a240`** | **00ff** | **ffb8** | 10e4 | a240 | **00ff 半标签滞留顶段 + ffff 主标签溢出次高段（下移 8 位）** |
| #25 | 09-11-17:58 | `0000000000000000` | 0000 | 0000 | 0000 | 0000 | 无标签保留（全零塌缩，对照项） |

四案间隔：#22→#23 1.97h，#23→#24 0.60h，#24→#25 0.87h。**同一颗 CPU179 上，3.45 小时内（14:31→17:58），同一 0xff/0xffff 沾染模式在四个不同 16 位段位置之间迁移**（[31:16] → [63:56]/[15:8] → [63:48]/[47:32] → 全零）。

这一迁移谱在物理上只有一类自然解释：**装载返回通路（L1D 出口 → bypass/移位网络 → RF 写口）的 lane 选通/定序错位**。理由：
- 固定坏位（SRAM 单元损伤）产生**位置不变**的位错误，无法解释标签位置逐案漂移；
- 随机翻转（粒子/噪声）不产生**结构保留**（ff ff 双字节整体存活）；
- lane 错位则是"数据不变、槽位错排"——每案错排量不同（0/8/16/32 位或全塌缩），恰好产生观测到的迁移谱。
- #25 的全零塌缩是同通路的另一极端表现（整组 lane 未驱动/选通到零源），与 SYNTHESIS §2.3 零塌缩族（6 案）互洽。

#24 的 `00ff|ffff` 双段形态是迄今最直接的"标签跨段错位"活体样本：真值高 16 位 0xffff 的一半（00ff 的 ff，即 bit47..40）留在顶段，另一半（bit39..32 的 ff）已溢出到次高段——**一个 0xffff 标签被从中间"撕裂"后错位重组**。

### 4.3 与谱系（SYNTHESIS 12 案 + 已完成案 20/21/22）形态四族的对照

SYNTHESIS §2.3 将 12 案归为四族：零塌缩族（6）、lane 错位族（3）、部分位保留族（2）、读写双向族。#24 的字节粒度标签错排归属 **lane 错位族**，且粒度判定比前三案（#1 16bit lane 循环移位、#5 +1 字节窗口、#7 ror16+0xa000）更精细：**#5 与 #24 同为"8 位（单字节）错位"粒度**——两案互相印证"错位量恰为一个字节"这一通路级粒度特征。

## 6. 反事实与软件排除

### 6.1 反事实推演（因无 vmcore，本节以不变式替代实测——降级声明重申）

- **若 x20 装载返回真值**（形如 `ffff_c7xx_xxxx_x000`，canonical + 4K 页对齐）：x27 = x1 + 真值仍为 canonical 内核地址（x1=ffffc7ef... 是 dump 中实际在手的 canonical rq 指针，其自身未被腐化已被加法闭合间接证明），`ldr x23,[x27,#0x120]` 正常读 `rq->cfs.avg` 字段，无 fault。**正确执行永不崩溃；崩溃 100% 归因于那一次装载读回**——与谱系 10 案 crash 实测反事实闭合同构，本案为推断版。
- **真值侧无法实测的补偿**：两条不变式（顶段 0xffff、低 12 位 0x000）被同时破坏，而 `__per_cpu_offset[50]` 真值必然同时满足两条（percpu 偏移是 4K 对齐的 unsigned long，内核地址）。**一条不变式被破坏即足以定罪装载返回值，本案两条同时被破坏且破坏方式结构化**——即使无 vmcore，"x20 ≠ 内存真值"仍是【实锤】（内存里的数组元素不可能既是页对齐又同时满足两条，更不可能以 ff 字节错排形态恰好凑成）。

### 6.2 软件成因排除

| 软件假设 | 排除证据 |
|---|---|
| 内核 bug（调度器/use-after-free 等） | ① Not tainted，官方 build #1（L2596），无第三方补丁；② 同一二进制在 191 颗其他核上运行同一代码路径亿万次零异常，仅 CPU179 崩（谱系含本案 16/16 案同核）；③ 软件 bug 不挑核 |
| 坏页/页表被改 | ESR=0x96000004、S1PTW=0（L2586）——fault 的是**数据地址翻译的 L0**，即地址本身非法（介于用户与内核区间，L2592），而非页表项被清；页表完好性由 fault 类型反证 |
| 竞态/内存序 | 受害路径为纯读侧（load→add→load），且坏值形态是**结构化标签错排**而非过期值（过期值仍是 canonical 指针，不会出现 00ff/ffb8 错排） |
| 编译器/指令解码错 | Code dump 五指令窗口与内核符号偏移逐条吻合（3.1 节），x0=0x32 与 w25 快照自洽；imm 解码反证闭合（3.4 节第 3 条） |
| 用户态进程肇因 | 上下文为 kworker 内核线程 worker_thread→schedule 空闲调度（2.3 节），与任何用户进程数据无因果 |

### 6.3 硬件侧非核内通路的排除（降级后仍成立的分）

- **DIMM/内存控制器**：ghes_edac 32 DIMM 在位监测（L2176-2177）1592s 零 CE/零 UE；且若 DIMM 坏，读错会发生在任何核——不会 16 案锁定 CPU179。
- **缓存一致性**：受害数据是 CPU179 私有的 `__per_cpu_offset[50]` 数组元素读出（该槽位的读者主要是做均衡决策的核），若为一致性协议缺陷，191 核对称受害，观测不符。
- **L1D 阵列驻留损伤**：谱系 #7 案（08-31）17 轮 L1D 禁用实验期间仍复发（SYNTHESIS §3），排除单点阵列损伤，支持通路级（时序/选通）缺陷——本案标签错排形态与该结论互洽。

## 7. 根因三级置信判定与跨案对照

### 7.1 判定

1. **现象层【实锤】**：CPU179 上 `__per_cpu_offset[50]` 装载返回结构化坏值 x20=00ffffb810e4a240（双不变式破坏 + ff 字节错排），经两条代数闭合的纯正确指令传播为 L0 translation fault，开机 1592s 致命。
   - 证据：dmesg L2581-2626（六要素）；algebra_out.txt 第一、二节（两项 mod 2^64 闭合均 True）；第四节（双不变式破坏）。
2. **通路归属【强推】**：CPU179 核内装载返回通路（L1D 出口→bypass/移位网络→RF 写口）的 lane 选通/定序错位，间歇性、无检错覆盖的 SDC。
   - 证据：标签迁移谱四案同核（4.2 节表）；错排结构保留排除随机翻转（4.1 节）；零应力背景排除累积模型（5.2 节）；RAS 零上报 + 软件排除（6.2/6.3 节）；谱系 12 案同指令族同核收敛（SYNTHESIS §2.1/§2.2）。
   - **降级说明**：本案无 vmcore，无法实测真值对照与全内存搜索（谱系 #8 案曾用"全内存无此值"加固），故由谱系同构 + 本案不变式推断维持【强推】而非【实锤】。
3. **物理位点【假设】**：bypass 网络 lane 选通 vs RF 写口字节使能 vs L1D 输出锁存——软件不可分辨。验证途径同谱系处置建议：offline CPU179 后前兆/崩溃应归零；裸机 load-verify 双核校验；厂商 shmoo/MBIST 复测 RF 与 bypass（重点：字节粒度选通路径）。
