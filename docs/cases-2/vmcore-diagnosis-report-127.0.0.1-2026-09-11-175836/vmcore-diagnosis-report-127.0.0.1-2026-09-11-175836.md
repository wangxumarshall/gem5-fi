## 1. 摘要与置信度

开机 **2777 秒（46.3 分钟）**后，CPU179 上的用户进程 mi-scavenger（PID 56594）在 futex 等待睡眠路径（`futex_wait → schedule → newidle_balance → load_balance → find_busiest_group`）中，执行 `__per_cpu_offset[]` 数组装载指令 `ldr x20, [x0, x25, sxtw #3]`（x25=6，读 CPU6 的槽，跨槽为调度域遍历正常行为），**装载返回值 x20 = 0000000000000000 完全零塌缩**。零偏移使下游加法退化为恒等（x27 = x1），致命装载 `ldr x23,[x27,#0x120]` 以 x1+0x120 寻址——FAR = ffffdee405e697e0 是 **canonical 但未映射**的地址：内核页表 walk 显示 pgd/pud 有效而 **pmd = 0**（L2 断链），触发 **level 2** translation fault 致命 Oops。这与前三案（#22/#23/#24，坏值 noncanonical → FSC=L0 "address between"）形成精确镜像：**同样的腐化点，因坏值形态不同而呈现完全不同的 fault 几何**。RAS/EDAC/GHES 全程零上报，无任何前兆日志。

**三级置信度**：
- 现象层（x20 装载返回零 → 恒等传播 → canonical 未映射地址 L2 fault）：**【实锤】**——dmesg 寄存器 dump + mod 2^64 逐位代数闭合（algebra_out.txt 第一~三节）+ 页表 walk 行（pmd=0）。
- 通路归属（CPU179 核内装载返回通路的零塌缩，非内存/软件/一致性）：**【强推】**——非零性不变式破坏 + 09-11 当日四案全在 CPU179（本案为当日第 4 案）+ RAS 零上报 + 谱系零塌缩族（#4/#6/#10/#11/#12 + 案 20）同构；但因本案无 vmcore，无法实测真值，故降一级。
- 物理位点（bypass/移位网络 vs RF 写口 vs L1D 出口锁存）：**【假设】**——软件不可分辨。

## 3. 指令级解剖

### 3.1 Code dump 五指令窗口反汇编（dmesg L2630）

```
f9400782   ldr  x2, [x28]                  // +0x128（上文，未参与致命链）
f879d814   ldr  x20, [x0, x25, sxtw #3]    // +0x130 ← __per_cpu_offset[x25] 装载（腐化点）
2a1903e0   orr  x0, wzr, w25               // +0x134（dump 时 x0=0x6，为后续循环所用）
8b14003b   add  x27, x1, x20               // +0x13c ← x20=0 使加法退化为恒等：x27 = x1
(f9409377) ldr  x23, [x27, #0x120]         // +0x140 ← 致命装载：读 rq->cfs.avg 等（offset 288）
```

注：括号内为 pc 处指令。x0 dump 值 0x6 与 x25=0x6 逐字吻合，证明执行流精确停留在 +0x140、且 w25/x0 此刻同持槽号 6——寄存器快照内部自洽。

### 3.2 x25=6 跨槽（CPU179 读 CPU6 的槽）——正常行为，非异常

`__per_cpu_offset[]` 装载的索引是**被考察 CPU** 的编号。CPU6 属 Node 0，CPU179 属 Node 7——负载均衡在顶层调度域（NUMA 域之上）遍历时跨 NUMA 读槽是标准动作（谱系 12 案的 w25/x25 分布 6~179 同理）。跨槽本身无异常，**异常仅在装载返回值**。

### 3.3 零塌缩的传播几何：canonical-but-unmapped

代数闭合（algebra_out.txt 第一、二节，全部 True）：

1. **x27 = x1 + x20**：`ffffdee405e696c0 + 0 = ffffdee405e696c0` ——闭合。但与 L0 案不同，这次 x27 **仍是 canonical**——零塌缩不改变地址合法性，只改变语义。
2. **FAR = x27 + 0x120**：`ffffdee405e696c0 + 0x120 = ffffdee405e697e0` ——闭合。AGU 正确。

语义解读：x1 是 percpu 静态基址形态的 canonical 指针（`ffffdee4....`，percpu 变量的"模板"地址）。正常执行时 `add x27, x1, x20` 把它平移 `__per_cpu_offset[6]`（CPU6 实例偏移）得到 CPU6 的 `rq` 实例；**x20=0 使平移丢失**，寻址落回静态模板区 + 0x120——该区在运行时未建立 PMD 映射（pmd=0，L2592），L2 断链。数据通路的零塌缩被页表几何忠实记录为 level 2 fault。

3. **反证非移位偏移**：若误用 imm=0x48 则 x27+0x48=...9708 ≠ FAR，排除解码错误假设。

**结论**：致命链条上除 `ldr x20`（+0x130）这一条装载指令的返回值外，其余每一步均被代数闭合证明正确执行。腐化点唯一且收口于装载返回通路。

## 6. 反事实与软件排除

### 6.1 反事实推演（因无 vmcore，本节以不变式替代实测——降级声明重申）

- **若 x20 装载返回真值**（`__per_cpu_offset[6]`，形如 `ffff_xxxx_xxxx_x000`）：x27 = x1 + 真值为 CPU6 实例的 canonical 已映射地址，`ldr x23,[x27,#0x120]` 正常读 `rq->cfs.avg`，无 fault。正确执行永不崩溃。
- **真值侧无法实测的补偿**：非零性 + canonical 双不变式同时破坏。`__per_cpu_offset[6]` 为零在语义上意味着"CPU6 的 percpu 区与静态区重合"——192 核 SMP 系统上不可能（各 CPU 实例必须互不重叠）。**即使无 vmcore，"x20 ≠ 内存真值"仍是【实锤】**。

### 6.2 软件成因排除

| 软件假设 | 排除证据 |
|---|---|
| 内核 bug | ① Not tainted，官方 build #1（L2596）；② 同一二进制在 191 颗其他核上运行同一代码路径亿万次零异常，仅 CPU179 崩（谱系含本案 17/17 案同核）；③ 软件 bug 不挑核 |
| 坏页/页表被改 | ESR=0x96000006、S1PTW=0（L2585）——fault 是数据地址翻译的 L2 断（pmd=0，L2592），页表本身完好（pgd/pud 有效且非零）；零偏移落入空洞是寻址语义错误，非页表损伤 |
| 竞态/内存序 | 受害路径为纯读侧（load→add→load）；零塌缩不是过期值（过期值仍是有效偏移，且 percpu 偏移在运行期不变，无竞态窗口） |
| 编译器/指令解码错 | Code dump 五指令窗口与内核符号偏移逐条吻合（3.1 节），x0=0x6 与 w25 快照自洽；imm 解码反证闭合（3.3 节第 3 条） |
| 用户态进程肇因 | futex 上下文只是引子；受害装载读的是内核全局数组 `__per_cpu_offset[6]`；谱系受害者横跨多种进程与上下文 |

### 6.3 硬件侧非核内通路的排除

- **DIMM/内存控制器**：ghes_edac 32 DIMM 在位监测（L2175-2176）2777s 零 CE/零 UE；且若 DIMM 坏，读错会发生在任何核——不会 17 案锁定 CPU179。
- **缓存一致性**：受害数据是 `__per_cpu_offset[6]` 数组元素读出，若为一致性协议缺陷，191 核对称受害，观测不符。
- **L1D 阵列驻留损伤**：谱系 #7 案 17 轮 L1D 禁用实验期间仍复发（SYNTHESIS §3），排除单点阵列损伤——零塌缩形态（整组 lane 选通到零源）与通路级选通缺陷互洽。

## 7. 根因三级置信判定与跨案对照

### 7.1 判定

1. **现象层【实锤】**：CPU179 上 `__per_cpu_offset[6]` 装载返回零（零塌缩），加法恒等传播使致命装载以 x1+0x120 寻址，FAR canonical 但 pmd=0（L2 断链），开机 2777s 致命。
   - 证据：dmesg L2580-2630（六要素 + 页表 walk）；algebra_out.txt 第一、二节（两项 mod 2^64 闭合均 True）。
2. **通路归属【强推】**：CPU179 核内装载返回通路的零塌缩（整组 lane 未驱动/选通到零源），间歇性、无检错覆盖的 SDC。

   - **降级说明**：本案无 vmcore，无法实测 `__per_cpu_offset[6]` 真值，故维持【强推】而非【实锤】。
3. **物理位点【假设】**：lane 选通网络全零源选通 vs RF 写口整字未使能 vs L1D 出口锁存清零——软件不可分辨。验证途径：offline CPU179；裸机 load-verify；厂商 shmoo/MBIST。
