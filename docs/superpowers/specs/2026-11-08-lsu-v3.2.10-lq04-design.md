# LSU v3.2.10 — LQ04 Design & Gate Decisions

**Status:** approved by the researcher on 2026-11-08 (AskUserQuestion answers recorded in the session).
**Baseline:** `lsu-platform-v3.2.9` @ `37692d2beffcb73fc9303ad9de4c6bb341d5de71`, binary
`303c610d2dcca81340f0feae58fc449c8550d1daac6ff965a3387efd2189a0c0`.
**Scope:** LQ04 only. The other 11 models, the 60 SampleRunIDs/RunIDs/SubTaskIDs/Seeds,
`ConfigFrozen=NO`, and the Warm-up/ROI `NEEDS_RESEARCHER_CONFIRMATION` status are unchanged.

## 1. Authoritative fault definition (unchanged)

From Excel v3.2.4 sheet 3 row 4 and sheet 4 row 4:

- FaultModelID `LQ04`; FaultConfigID `LQ04-CFG01`; SubTaskID `LQ04-F0-W2-S01`.
- Location: LQEntry lifetime management, after `executeLoad` and before the memory
  response.
- Target fields: `LQEntry::_valid` and `LQEntry::_request`.
- Normal: `valid=1`, `request=<in-flight request>`.
- Fault: `valid=0`, `request=nullptr`.
- Constraints: do not pop; do not free or reuse the entry early; the entry stays
  invalid until its original commit/squash lifetime ends; one target Load; one
  injection; addresses, access size and returned data are untouched.

The implementation must not silently widen or narrow this definition.

## 2. Source-audit conclusion (evidence, file:line)

Audit target: `CHAOS/gem5/src/cpu/o3/lsq_unit.{hh,cc}`, `lsq.{hh,cc}`.

- `LSQEntry` (nested `LSQUnit::LSQEntry`): `lsq_unit.hh:95-147`.
  `_valid` is written only by `set()` (`:133`) and `clear()` (`:124`).
  `_request` is written by `setRequest()` (`:138`), `clear()` (`:123`), the
  destructor (`:112`), `LSQRequest::install()` (`lsq.cc:1115-1125`), and
  `read()` (`lsq_unit.cc:1554`).
- Allocation: `insertLoad` `lsq_unit.cc:372-440`; generation is
  `++lqEntryGeneration` (`:388`), stored on both entry and DynInst.
- Execute/send: `executeLoad` `lsq_unit.cc:697-767` → `initiateAcc()` →
  `LSQ::read`/`pushRequest` builds the `LSQRequest` and sends it.
- Response: `LSQUnit::recvTimingResp` `:97-108` → `LSQ::recvTimingResp`
  `lsq.cc:449-464` → `LSQRequest::recvTimingResp` `lsq.cc:1248-1253` →
  `LSQUnit::completeDataAccess` `:110-232`. The request is recovered from
  `pkt->senderState` (`:100`, `:113`) and the instruction from
  `request->instruction()`; **the response path never reads the LQEntry**.
- Commit: `commitLoad` `:859-885` (asserts `front().valid()` at `:862`),
  `commitLoads` `:887-896` (asserts at `:890`).
- Squash: `squash` `:1111-1161`; clears and pops every entry above the squash
  point; `clear()` calls `freeLSQEntry()` when `_request != nullptr`.
- Request ownership: `LSQRequest` is self-managed (`lsq.hh:539-588`); it is
  deleted only after `freeLSQEntry()`/`discard()` **and** zero outstanding
  packets. `DynInst::savedRequest` is a raw back-pointer (`dyn_inst.hh:370`).

### Answers

**A. Clearing `_valid`.** The response still finds the request through
`pkt->senderState`, is not dropped, causes no replay and no wrong association.
The load completes normally. At commit (or drain) the invariant
`assert(front().valid())` fires, aborting gem5 — an unrecoverable simulator
state, not an architectural effect. If the entry is squashed first, `squash()`
completes (it never checks `valid()`), then `clear()`/`pop_back()`.

**B. Clearing `_request`.** No dangling pointer and no use-after-free: every
reader guards (`checkSnoop` `:526-542`, `checkViolations` `:656-660`,
`startStaleTranslationFlush` `:1478-1499`). But the entry is the only owner
that hands the request to `freeLSQEntry()` at commit/squash; nulling it leaks
one `LSQRequest` and skips stale-translation handling.

**C. Not popping / not reusing.** The circular-queue size is unchanged, so
occupancy, head/tail and back-pressure are unchanged; `insertLoad` cannot reuse
the slot until `pop_front`, and its `assert(!back().valid())` stays satisfied.
The only unrecoverable part is the commit-time `valid()` invariant above.

**D. Observable propagation.** Under the literal definition there is no
response loss, no wrong response binding, no replay induced by the fault and
no data corruption: the response is bound by `senderState` and delivers the
correct payload. The literal fault's only effects are (i) the commit-time
assert abort, or (ii) with the invariant handled, a trace-visible
invalid-entry interval plus the load's normal (correct) writeback. This is an
honest **negative** result for the research question; it must not be reported
as SDC.

## 3. Gate verdict and researcher decisions

Verdict: **IMPLEMENTABLE_WITH_CONDITIONS**. No UAF and no dangling request;
but the literal definition violates the commit invariant and does not produce
the Excel's hypothesized response loss.

Researcher decisions (2026-11-08):

1. **D1 — Response semantics:** literal field fault. Do **not** call
   `discard()` and do **not** drop the response. Expected terminal is
   `MASKED` when the target commits; record the sender-state association as
   positive evidence. Do not manufacture SDC.
2. **D2 — Commit integrity:** keep `valid=0`/`request=nullptr` for the whole
   interval; preserve the request in an opaque `LQEntry` side channel and
   restore it exactly at the commit/squash boundary, then let the normal
   `clear()` free it. Do not pop early. The only invariant sites that may
   accept the explicitly corrupted entry are the `commitLoads()` pre-loop
   check (`lsq_unit.cc:890`) and `drainSanityCheck()` (`:343`); `commitLoad()`
   restores before its own `assert(front().valid())`. No other assertion is
   relaxed.
3. **D3 — Target events:** build a new workload `lq_lifetime_ordinal` whose
   first five eligible Loads are five explicitly constructed anchors (distinct
   PC, address, data, destination register and consumer). Record its SHA256 and
   re-validate the Oracle. The original `lq_lifetime` remains archived.
4. **D4 — Ordinal semantics:** `EventOrdinal` is the 1-based ordinal of the
   eligible Load stream (eligible = Load whose LQ entry is valid and whose
   request exists at the end of `executeLoad`). No seeded-tier selection and
   no fallback to another event.
5. **D5 — Trace honesty:** record injection, entry-state change, response
   association, writeback, commit, restore/free and consumer edges. Separate
   `RecordIntegrity`, `TraceCompleteness` and `PropagationCoverage`.
   `PROPAGATION_VERIFIED=1` requires a real consumer edge; a lifecycle-only
   chain must remain `PROPAGATION_COVERAGE=LIFECYCLE_ONLY`.
6. **D6 — Identity freeze:** keep all 60 SampleRunIDs/RunIDs/SubTaskIDs/Seeds.
   Only LQ04's workload path/SHA/Oracle/status cells change.

## 4. Workload design (`lq_lifetime_ordinal`)

- `_start` is hand-written in AArch64 assembly with no libc and no dynamic
  loader. Its first instructions are five loads from a six-entry `.data`
  anchor table; no data load precedes them.
- Anchors: A1 `[tbl+0]`, A2 `[tbl+8]`, A3 `[tbl+16]`, A4 `[tbl+24]`,
  A5 `[tbl+32]`, loaded into x2–x6 and passed to `main` in x0–x4.
- `main(a,b,c,d,e)` uses each value in a different operation (multiply, XOR,
  add, shift-mix, compare) so the five consumers differ; then runs the
  original 4096-byte/64-iteration loop and an A5 guard check.
- Output is a single line `checksum=0x%016llx` written with the raw `write`
  syscall; exit with the raw `exit` syscall.
- Acceptance: the first five `lq_lifecycle action=alloc` records in a
  count-only run have five distinct PCs/addresses and correspond to the five
  anchors; the six no-fault controls reproduce the same checksum as the host
  binary and exit 0.
