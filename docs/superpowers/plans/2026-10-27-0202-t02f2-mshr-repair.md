## 根因（阶段1 确认，全部有直接证据）

**结论**：gem5 `BaseCache::recvTimingResp` 对 **UnCacheable 写的「错误响应」**分类错误，
落入要求 MSHR 的路径后断言失败。这是 gem5 自身的协议处理缺口，与 CHAOS 注入器无关
（注入器从不触碰 cache 协议内部状态）。

### 证据链（三方印证）

1. **断言处**（`CHAOS/gem5/src/mem/cache/base.cc:782-783`）：
   `MSHR *mshr = dynamic_cast<MSHR*>(pkt->popSenderState()); assert(mshr);`
   其上一分支（`:752-757`）只在 `pkt->isWrite()` 为真时才处理 UC 写。
2. **真实 debug 日志**（诊断复现 `runs/lsu/0202_t02f2_mshr_diag1_20261027T010327/logs/debug2.txt`，
   断点 tick `240017009067`）给出完整事务链：
   ```
   240016798611 l1d-cache-0: access for WriteReq [1c191000:1c191001] UC
   240016798944 l1d-cache-0: sendWriteQueuePacket: write WriteReq [1c191000:1c191001] UC
   240016798944 l2-cache-0:  access for WriteReq [1c191000:1c191001] UC
   240016802607 l2-cache-0:  sendWriteQueuePacket: write WriteReq [1c191000:1c191001] UC
   240016802607 board.iobridge.cpu_side_port: recvTimingReq: WriteReq addr 0x1c191000
   240016958118 board.iobridge.mem_side_port: recvTimingResp: BadAddressError addr 0x1c191000
   240017009067 l2-cache-0: recvTimingResp: Cache received BadAddressError [1c191000:1c191001] UC with error
   240017009067 l2-cache-0: recvTimingResp: Handling response BadAddressError [1c191000:1c191001] UC
   ```
   ⇒ 一次 **UC 写**经 write buffer（`sendWriteQueuePacket`，**不分配 MSHR**）发到
   `0x1c191000`，由 iobus 的 default `badaddr_responder`（IsaFake, `ret_bad_addr`）回
   **BadAddressError**；该响应到达 L2 的 `recvTimingResp` 后断言。
3. **flags 事实**（`CHAOS/gem5/src/mem/packet.cc:216`）：
   `{ {IsResponse, IsError}, InvalidCmd, "BadAddressError" }` —— **不含 IsWrite**。
   故 `pkt->isWrite()` 为假 ⇒ 跳过 `handleUncacheableWriteResp` ⇒ 落到 `assert(mshr)`。
   而 UC 写走 write buffer、**永不分配 MSHR**（`base.cc:2365` 是 MSHR 唯一入栈点，
   `sendWriteQueuePacket` 对 UC 写「forward as is」不 push sender state）⇒ 必然失败。

### 为什么故障会走到这里（T02 fault model 的正常后果，非缺陷）

T02 只翻 TLB 表项的 `pfn`（`CHAOSArmTLB.cc:679`），**不重算属性**（符合模型定义，不得修改）。
被翻的是 **UART0 的 D-Side TLB 表项**（`old_pfn 0x1c090` = PA `0x1C090000`，即 PL011 UART0），
翻成 `0x1c191000`：该地址仍落在 `board.iobridge` 的 range `0x0C000000–0x20000000` 内，
但 iobus 上**没有**对应设备 ⇒ 命中 iobus 的 default `badaddr_responder`。
属性保留 Device/nonCacheable ⇒ 请求被标 **UNCACHEABLE** ⇒ 走 UC 写路径。

### 不采取的方向（及原因）

- 不删/绕过 `assert(mshr)`；不吞掉该响应；不伪造 MSHR（红线）。
- 不改 T02 fault model（不得改 bit 数/属性语义）——「只翻 pfn」是模型定义。
- 不在 `recvTimingResp` 末尾加兜底 catch/return —— 而是在**同一分类点**补全分类：
  error 响应按其**真实来源**（write-buffer/UC 写）路由到既有 `handleUncacheableWriteResp`，
  与成功的 UC 写响应同一条路径，错误照常经 `schedTimingResp` 上报 CPU，不被吞。

### 顺带发现（独立缺陷，另行修复）

`tools/lsu_l5_classify.py:83` 的 abort 回退用 `len(re.findall(r"Site: ", text))` 计数，
把 `arm_tlb_lookup_tier` **诊断行**也计入 ⇒ 本次 `injected=3`/`activated=3` 是错的，
真实应用注入为 **2** 次（与流内 fault 1/2 一致）。**更正**：先前诊断报告
`R0202-T02F2-SEED1-DIAG.md` §8-L1 所称「第 3 次注入事件丢失」**不成立** ——
该次注入根本不存在，流未丢失任何已激活 fault 的事件。
