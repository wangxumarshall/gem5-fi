# 案例复盘：CPU 179 "浮点 SDC" 故障的完整取证与微架构根因重定位

## 1. 故障背景与现象概述

一台生产环境的 192 核 ARM64 服务器在 22 天内发生持续性崩溃。排查期间，我们通过四种独立方法（OpenDCDiag 负载循环、欠压+simd memcpy 压测、高并发 memcpy 检测、stress-ng+opendcdiag 压测）在同一硬件上稳定复现了 SDC（静默数据损坏）故障，累计复现 147 次。

为避免口径混淆，先交代三组数字的关系：12 份 vmcore 均来自 22 天生产期的现场 panic；147 次复现全部来自实验室四种触发方法；其中方法二/三压测期间的 17 次崩溃完成了寄存器级取证（第 4 节）。另外两点限定："独立"指触发负载彼此独立——四种方法施加的都是同一核上的 load/store 激励，并非四种独立探针；"100% 收敛于 CORE 179"的结论以各核等量暴露（全核同负载）为前提，方法一通过两组全核失败率实验直接验证了这一前提。

故障呈现三个核心特征：

* 单核收敛：四种触发方法、上百次测试失败均 100% 收敛于 CORE 179，其余 191 个核零故障。
* RAS 告警静默：硬件 RAS 体系（GHES/ghes_edac/BERT/SEL）在全生命周期内未产生任何相关告警。
* 间歇性随机触发：12 次内核 panic 的开机存活时长跨度极大（最长 149.3 小时，最短 0.116 小时，相差 1285 倍），无单调恶化趋势。这推翻的是"随时间单调恶化"的渐进模型；间歇性触发与边际时序缺陷相容——无论该边际是先天制造缺陷还是老化引入，都无法从存活时长分布中区分（缺陷起源问题见第 5 节）。

## 2. 现场数据与表象分析 (vmcore 侧)

对收集到的 12 份 vmcore 的解剖显示，崩溃路径高度一致，且与特定软件栈无关：

* 同构的崩溃点：11/12 的崩溃发生在同一条指令 `find_busiest_group+0x140`（CFS 调度器负载均衡的 per-CPU 遍历体，具体为 `ldr x23,[x27,#0x120]` 读 `rq->cfs.load_avg`）。需要说明：崩溃点的同构是抽样偏差而非机制证据——`find_busiest_group` 是内核最热的 per-CPU 索引装载之一，若坏值随机命中任意 load，"哪条装载的坏值致命"由指令执行频度决定；致命点集中于调度器热路径，恰与"随机命中、热度加权显性化"的预期一致，反而强化了随机 SDC 的定性。
* 同源的异常机制：唯一的一例例外发生于 `bio_add_page+0xf0`。路径不同，但坏值同样来源于一条索引型装载（Load）指令的返回值。样本量仅 1，此处的"同源"只能作弱佐证；真正坐实"任意 load 均可受害"的是第 4 节的 memcpy 复现。
* 软件环境无关：受害进程横跨 kworker、swapper、rcu_sched、systemd-coredump 等 6 种截然不同的身份，排除了特定软件逻辑触发的可能。

## 3. "浮点 SDC" 表象的动摇 (方法一解析)

初期，OpenDCDiag 循环测试（方法一）给出了强烈的"浮点运算单元损坏"表象：17 分钟的无限循环全量测试中仅出现 2 次（2/2178）失败，全部集中在 Eigen 库的 `eigen_sparse`（double 精度稀疏 Cholesky）与 `eigen_gemm_float`，且均发生在 CPU 179。

本节标题用"动摇"而非"证伪"：方法一自身的证据只能削弱 FPU 假设，不足以裁决它；裁决由第 4 节的跨方法证据完成。我们执行了六层假设排除，每一层排除的都是特定类别的成因，而非全部可能：

1. 排除确定性软件 Bug：固定失败 seed 在 Core 179 单跑 9000+ 次全过，排除的是"输入确定、单核可复现"的软件逻辑错误；时序依赖的并发 bug、跨核干扰不在此层的排除范围内。
2. 排除输入数据边界问题：全核输入相同数据，仅 Core 179 失败（两组实验：285/285 和 140/140 的失败率均被 179 核包揽）。
3. 削弱（而非排除）浮点流水线假设：测试矩阵中的密集 GEMM（float/double）、SVD、纯 FMA、整数/CRC 测试全部零失败，唯一起效的仅为稀疏 Cholesky 的 numeric factorize 阶段。但密集 GEMM 与稀疏 Cholesky 的指令交错截然不同，这只排除了"任意浮点序列皆触发"的强故障形态，排除不了"指令序列特异"的浮点数据通路故障。
4. 定位至字节级：损坏固定发生在求解结果向量 `x[0]`（固定栈地址），表现为 bit 21–32 连续 12 位字段损坏，跨越字节边界，而非单 bit 翻转。当时的取证未建立坏值与邻近真实字节流的对照（该对照面在第 4 节才建立），故此阶段只能定性为"多位、字节通路粒度"的损坏，"混叠"的定性有待第 4 节验证。
5. 最小复现用例锁定：并非浮点运算出错，而是特定指令交错（cdiv 条件分支 + rank-1 update 标量 FMA + 间接地址生成 + 长存活 d4 累加器）触发。
6. 状态泄漏签名（弱证据）：numeric-only 失败率约为 compute-both 的 4 倍。这与"symbolic 阶段重做会刷新某个微架构状态、numeric 阶段发生泄漏"的假说相容，但也与"numeric-only 单位时间内易感交错执行次数更多"等执行密度差异相容，此处仅作方向性线索。

阶段结论：方法一的证据链将故障从"浮点运算单元"收窄到"特定指令交错触发的数据通路异常"，但仅凭方法一无法区分"浮点数据通路自身故障"与"公共数据搬运网络故障"——裁决需要整数/访存负载上的同类失败，即第 4 节的跨方法证据。可以确定的纠偏是：浮点测试报错，仅仅因为 Eigen 测试是当时唯一在跑的浮点密集且涉及复杂数据搬运的负载。

## 4. 真实载体：数据搬运与选路通路 (方法二/三解析)

将 CPU 核心电压拉偏 30mV、接近欠压阈值并运行 memcpy 压测，直接暴露了底层数据通路的缺陷。此处必须先交代对照：对健康核心施加欠压本身即可制造 SDC，故"欠压下失败"不构成 CORE 179 存在先天缺陷的证据；真正的证据是差分——同压、同负载、等量暴露下，其余 191 个核零失败，唯 CORE 179 持续产生坏值。欠压的角色是把 179 本已边际的通路推过阈值，而非制造新缺陷。

17 次崩溃的寄存器取证显示，导致 panic 的是硬件 SDC 的典型特征：同一指令（同源地址），每次读出不同的非法地址（坏值）。将 crash 直读的坏值与内存真值（`__per_cpu_offset[]`）比对，提取出两类直接指向数据通路的签名：

1. 零塌缩（Zero Collapse）：非零内核指针装载为全零（如内存值为 `0xffffa89017090000`，寄存器值为 `0x0`）。真值对照（内存确实非零）首先排除了"读早于写"的架构级时序竞争；剩余的解释落在微架构数据交付段——要么该数据拍被 LSU/填充缓冲丢弃后以零值顶替交付，要么总线该拍未驱动且接收端弱下拉读零（浮空本身不保证读零）。两种亚型共同指向"数据拍未送达"。
2. 撕裂移位（Tear & Shift）：寄存器值等于被读数组内存值错相位 N 字节处的真实字节流。这一签名有两种读法：数据选路错误（SRAM 阵列内容无误，错拍发生在字节选路网络——对齐 mux/字节使能/合并缓冲指针），或地址路径错误（AGU/地址加法器算出 addr+N，从错误地址读回了正确的数据）。二者均收窄在 LSU 内部：本例 `ldr x23,[x27,#0x120]` 偏移为立即数，架构地址由基址寄存器唯一决定，故障必在地址生成末级或其后的数据选路段。当前取证粒度无法在"选路错误 vs 寻址错误"间做最终裁决，故候选定位取两者的并集：从地址生成末级经字节选路到拍交付的 LSU 内部数据交付通路。

需要标注一条取证边界：两类签名提取自方法二/三的复现崩溃；第 2 节对生产期 12 份 vmcore 的解剖未建立真值对照面。将复现签名归因于生产期故障的桥接依据，是单核收敛与共同机制特征（同一装载读出不同坏值）。

四种方法复现的故障 100% 锁定 Core 179。若 147 起事件由 $k$ 个相互独立的缺陷引起，它们全部落在同一物理核（1/192）上的联合先验为 $(1/192)^{k-1}$，当 $k\ge 2$ 时可忽略——"多个独立缺陷分踞多核、恰好都在 179 显形"的解释由此排除。但该论证有两条边界：其一，它证明的是这些事件共享同一**物理根源**（同核、同局部区域），而非同一**缺陷点**；其二，"缺陷在核间独立均匀分布"的前提本身与系统性局部成因（电源域边际、局部缺陷聚集使同一核多条通路同时变边际）相悖，而后者正是第 5 节保留的待裁决假说之一。换言之，概率论证排除的是多缺陷独立假说，对"单点缺陷 vs 单一区域性边际"无裁决力。

将根因从功能单元收敛至数据交付通路后，我们用"签名 × 假设"矩阵检验候选结构——每个假设必须解释全部签名才能存活：

| 候选结构 | 零塌缩 | 撕裂移位 | bit21–32 位域损坏 | 状态泄漏(4×) | no-op 相位敏感 |
|---|---|---|---|---|---|
| LSU 数据交付通路（地址生成末级/填充缓冲/对齐 mux/字节使能） | ✓ 拍未送达、零值顶替 | ✓ 错拍合并/错相位选路 | ✓ 字节通路粒度损坏 | △ 无天然解释 | ✓ |
| 旁路交叉矩阵/写端口 | ✗ 旁路交付活寄存器值，难为全零 | ✗ 无法产生错位真实字节流 | ✓ 数据混叠净效果一致 | △ | △ |
| 寄存器重命名表（RRT） | △ 偷映射可交付恰好为零的寄存器 | ✗ 交付的是另一活寄存器，非错位内存字节流 | ✓ 长存活累加器是偷映射典型目标 | ✓ 最自然解释 | △ |

补充证据与限定：

* STLF 是 LSU 数据交付通路在 memcpy 场景下的特化形态：memcpy 触发的四个必要条件全是 store→load 性质；翻转位点全在 reload 指令；插入一条 no-op 指令可使触发率从 100% 暴跌至 10%（典型的时序相位竞争特征）。gem5 LSQ 转发的相位偏移测试中，错开一步即 100% SDC，与现场现象一致。但需说明：现场 12 份 vmcore 的故障装载（`__per_cpu_offset[]`、`rq->cfs.load_avg`）并无证据表明紧跟同地址 store——`__per_cpu_offset[]` 在启动后几乎不再被写——字面意义的 store→load 转发不覆盖现场崩溃点；STLF 实验定位的是同一交付通路（填充缓冲/LSU 数据路径）的边际时序，而非"转发"这一特定机制。
* gem5 注入实验提供的是**相容性证据**（"若该结构存在此类缺陷，症状会如此"），不是独立确证：背靠背 FMA 依赖链的中间值在旁路网络流动、不回读物理寄存器堆，对 PRF 的注入被操作数转发掩蔽、唯一暴露点在转发网络——这证明旁路矩阵**能够**产生方法一式的数据混叠，但不能证明它**就是**本次故障的载体。

矩阵的读法：LSU 数据交付通路是唯一在全部签名上无硬伤的候选（状态泄漏签名上仅弱解释）；RRT 被撕裂移位一票否决；旁路矩阵被零塌缩与撕裂移位双重否决。但 LSU 交付通路内部没有任何单一节点能同时自然解释全部签名——零塌缩指向数据使能/拍交付，撕裂移位指向字节选路或寻址末级，状态泄漏指向类调度器状态。这恰是第 5 节结论的论证必然落点：不是某个单一结构的静态缺陷，而是同一边际时序在交付通路不同逻辑节点上的多点显现。

至此完成第 3 节悬置的裁决：现场与复现中的坏值大量出现在整数索引装载（`ldr x23,[x27,#0x120]`、`__per_cpu_offset[]` 读、memcpy reload）上，浮点与整数负载唯一共享的是数据搬运与选路基础设施。"浮点单元（FPU/ALU）自身故障"假设至此才被跨方法证据证伪。

## 5. 最终结论

同一边际时序毛刺，落在数据交付通路的不同逻辑节点上，会呈现出截然不同的失败模式（落在 mux 给撕裂移位，落在数据使能给零塌缩，落在旁路给寄存器混叠）。软件层面的取证无法区分两件事：其一是缺陷的覆盖范围——单点缺陷（如某个 Via 通孔退化）还是单一边际区域（局部电源域导致多条临界路径同时违例）；第 4 节的概率论证排除了多缺陷独立假说，但恰在这两种假说之间无裁决力，需要原厂的 ATE/Shmoo 测试裁决。其二是缺陷的起源——先天制造边际还是老化引入；第 1 节的存活时长分布只否定了"单调恶化"模型，不否定老化作为缺陷引入机制。

对微架构排查体系而言，本案例确立了一个纠偏：浮点负载上发生的 SDC 不等于浮点单元（FPU）的 SDC。但这一命题的证明依赖跨方法证据链——第 3 节只完成动摇，第 4 节才完成证伪；单凭"纯浮点探针零失败"是不够的，因为那排除不了指令序列特异的浮点通路故障。当故障位于公共数据搬运网络（如 LSU 数据交付通路或旁路矩阵）时，任何经过该网络的功能单元都可能成为"背锅者"。指令只是激励的载体；建立"真值 vs 实收"的内存对照面，才能穿透业务表象，定位数据链路的根因。
