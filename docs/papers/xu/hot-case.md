# 案例复盘：CPU 179 "浮点 SDC" 故障的完整取证与微架构根因重定位

## 1. 故障背景与现象概述

一台生产环境的 192 核 ARM64 服务器在 22 天内发生持续性崩溃。排查期间，我们通过四种独立方法（OpenDCDiag 负载循环、欠压+simd memcpy 压测、高并发 memcpy 检测、stress-ng+opendcdiag 压测）在同一硬件上稳定复现了 SDC（静默数据损坏）故障，累计复现 147 次。

故障呈现三个核心特征：

* 单核收敛：四种触发方法、上百次测试失败均 100% 收敛于 CORE 179，其余 191 个核零故障。
* RAS 告警静默：硬件 RAS 体系（GHES/ghes_edac/BERT/SEL）在全生命周期内未产生任何相关告警。
* 间歇性随机触发：12 次内核 panic 的开机存活时长跨度极大（最长 149.3 小时，最短 0.116 小时，相差 1285 倍），无单调恶化趋势，推翻了早期关于"硬件渐进性老化恶化"的假设。

## 2. 现场数据与表象分析 (vmcore 侧)

对收集到的 12 份 vmcore 的解剖显示，崩溃路径高度一致，且与特定软件栈无关：

* 同构的崩溃点：11/12 的崩溃发生在同一条指令 `find_busiest_group+0x140`（CFS 调度器负载均衡的 per-CPU 遍历体，具体为 `ldr x23,[x27,#0x120]` 读 `rq->cfs.load_avg`）。
* 同源的异常机制：唯一的一例例外发生于 `bio_add_page+0xf0`。路径不同，但坏值同样来源于一条索引型装载（Load）指令的返回值。
* 软件环境无关：受害进程横跨 kworker、swapper、rcu_sched、systemd-coredump 等 6 种截然不同的身份，排除了特定软件逻辑触发的可能。

## 3. "浮点 SDC" 伪标签的证伪 (方法一解析)

初期，OpenDCDiag 循环测试（方法一）给出了强烈的"浮点运算单元损坏"表象：17 分钟的无限循环全量测试中仅出现 2 次（2/2178）失败，全部集中在 Eigen 库的 `eigen_sparse`（double 精度稀疏 Cholesky）与 `eigen_gemm_float`，且均发生在 CPU 179。

为了验证该表象，我们执行了六层假设排除法：

1. 排除软件 Bug：固定失败 seed 在 Core 179 单跑 9000+ 次全过，排除 Eigen 5.0 确定性 Bug。
2. 排除数据边界问题：全核输入相同数据，仅 Core 179 失败（两组实验：285/285 和 140/140 的失败率均被 179 核包揽）。
3. 排除浮点流水线本身：测试矩阵中的密集 GEMM（float/double）、SVD、纯 FMA、整数/CRC 测试全部零失败，唯一起效的仅为稀疏 Cholesky 的 numeric factorize 阶段。
4. 定位至字节级：损坏固定发生在求解结果向量 `x[0]`（固定栈地址），表现为多位 21-32 bit 的数据混叠，而非单 bit 翻转。
5. 最小复现用例锁定：并非浮点运算出错，而是特定指令交错（cdiv 条件分支 + rank-1 update 标量 FMA + 间接地址生成 + 长存活 d4 累加器）触发。
6. 状态泄漏签名：numeric-only 失败率约为 compute-both 的 4 倍。说明 symbolic 阶段重做会刷新某个微架构状态，指向乱序引擎的跨迭代状态泄漏。

阶段结论：浮点测试报错，仅仅因为 Eigen 测试是当时唯一在跑的浮点密集且涉及复杂数据搬运的负载。纯浮点探针测试的 0 失败，将"浮点计算单元（FPU/ALU）故障"猜测证伪。

## 4. 真实载体：数据搬运与选路通路 (方法二/三解析)

将 CPU 核心电压拉偏 30mV，接近欠压阈值并运行 memcpy 压测，直接暴露了底层数据通路的缺陷。

17 次崩溃的寄存器取证显示，导致 panic 的是硬件 SDC 的典型特征：同一指令（同源地址），每次读出不同的非法地址（坏值）。将 crash 直读的坏值与内存真值（`__per_cpu_offset[]`）比对，提取出两类直接指向数据通路的签名：

1. 零塌缩（Zero Collapse）：非零内核指针装载为全零（如内存值为 `0xffffa89017090000`，寄存器值为 `0x0`）。这表明数据拍未送达：要么总线该拍未驱动（浮空读零），要么填充缓冲以零值顶替。
2. 撕裂移位（Tear & Shift）：寄存器值等于被读数组内存值错相位 N 字节处的真实字节流。这证明 SRAM 阵列内容无误，错拍发生在字节选路网络（对齐 mux / 字节使能 / 合并缓冲指针）。

四种方法复现的故障 100% 锁定 Core 179。假设存在 $k$ 个独立的硬件缺陷，它们同时落在同一个物理核（1/192）上的先验概率为 $(1/192)^{k-1}$。147 起可归因事件 100% 为单核故障，数学上可断定：方法一的"浮点 SDC"与 memcpy 的"Load-Store SDC"必然共享同一物理缺陷。我们将疑似的浮点单元 SDC 故障的根因收敛至所有功能单元共用的数据搬运与选路基础设施，评估如下：

* STLF（存储转发数据通路）：memcpy 触发的四个必要条件全是 store→load 性质；翻转位点全在 reload 指令；插入一条 no-op 指令可使触发率从 100% 暴跌至 10%（典型的时序相位竞争特征）。gem5 LSQ 转发的相位偏移测试中，错开一步即 100% SDC，与现场现象一致。
* 旁路交叉矩阵/写端口：gem5 注入实验证明，背靠背 FMA 依赖链的中间值在旁路网络流动，不回读物理寄存器堆。对 PRF 的注入被操作数转发掩蔽，唯一的暴露点在转发网络。这与方法一观察到的"数据混叠"净效果一致。
* 寄存器重命名表（合法域替换）：可以解释方法一的状态泄漏签名（长存活累加器正是重命名偷映射的典型目标），但解释不了方法二/三中的"撕裂移位"：重命名替换交付的是另一个活寄存器，而非错位的真实内存字节流。

## 5. 最终结论

同一边际时序毛刺，落在数据交付段的不同逻辑节点上，会呈现出截然不同的失败模式（如：落在 mux 给撕裂移位，落在数据使能给零塌缩，落在旁路给寄存器混叠）。软件层面的取证无法区分这是单点缺陷（如某个 Via 通孔退化）还是单一边际区域老化（局部电源域导致临界路径违例），这需要原厂的 ATE/Shmoo 测试裁决。但对微架构排查体系而言，本案例确立了一个纠偏：浮点负载上发生的 SDC 不等于浮点单元（FPU）的 SDC。当故障位于公共数据搬运网络（如 STLF 或旁路矩阵）时，任何经过该网络的功能单元都可能成为"背锅者"。指令只是激励的载体；建立"真值 vs 实收"的内存对照面，才能穿透业务表象，定位数据链路的根因。
