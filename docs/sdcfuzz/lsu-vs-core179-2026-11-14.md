# LSU 生成流 vs 179 核触发流：ACE/IBR/SAD 指标对比（2026-11-14）

- 触发流：OpenDCDiag `neon_rot_ldr_at_top_rowmajor`（`179core-docs/test.c` 与
  `0102单板CPU179核微架构级SDC诊断报告.html` 对应的用例）
- 生成流：`tools/autousens.py target --structure l1d` 与 `sdcfuzz` 的
  `l1d-load-stream` / `l1d-store-hot` 模板
- 测量：gem5 O3 + `--kp920_proxy` + RF ACE / L1 ACE / FU IBR / SAD，ROI 由
  `m5_work_begin(7, 0)` 界定；主机 `sdc-0103`
- 工具：`tools/lsu_compare.py`；数据：`m5out/lsu-compare/lsu_compare.json`

## 结论先行

1. **两个目标已经分叉**：sdcfuzz 生成流把"每千指令访存事件"做到 890–980，
   是触发流（292）的 3.0–3.4×；但 L1D ACE 覆盖率只有触发流的 1/40 到
   1/140000（0.0000015–0.0055 vs 0.2204）。
2. **触发流的特征是"大工作集 + 长重用距离"**：6 个 8 KiB 数组在 64 KiB L1D
   里轮转（96 KiB 足迹），每次 sweep 反向扫描，L1D ACE 0.2204（去掉校验扫描
   后 0.4106）。生成流都挤在 512 B 缓冲里，L1D 命中率 99%，ACE 几乎为 0。
3. **IBR 看不到这条触发流的算术主体**：触发流每元素 4 条 128-bit 整型 NEON
   运算（add/eor/and/orr），不在 intAlu/intMult/intDiv/fpAdd/fpMult 五类里；
   1.93e-1 的 `IBRalu` 全部来自标量循环控制与校验扫描。
4. **`target --structure l1d --top 3` 目前会生成病态流**：`ldxr` 与同地址
   `str` 混排触发 LL/SC 重试，每提交一条指令要 7.85 次发射尝试，LQ 占用
   0.961，提交率掉到 0.43 IPC；单独 `ldxr`（top=1）则完全正常（3.75 IPC、
   iss/cmt 1.002）。这是组合阶段缺少别名约束，不是 LSU 压力。
5. **RF ACE 方向相反**：触发流 `RFint` 0.0826，高于生成流（0.0188–0.0550）；
   但 `RFvec` 只有 0.0013，即使 ROI 内有 8.9 万次向量寄存器访问——向量 ACE
   的 64-bit 通道粒度对 128-bit 触发流近乎失明。

## 1. 对比对象

### 1.1 179 核触发流

`neon_rot_ldr_at_top_rowmajor` 的内循环，每个元素：

- 3 × `ldr q`（scratch、srcA、srcB，各 16 B）
- 1 条 128-bit 整型 ALU，按 `i % 4` 轮转 add/eor/and/orr
- 2 × `str q`（temp、dst）
- 每轮 sweep 后整段比对 dst 与 golden；奇偶 sweep 方向相反

`179core-docs/test.c` 依赖 Sandstone（`sandstone.h`、`TEST_LOOP`、
`memset_random`），不能直接编译。本仓库的
`workloads/directed/core179_neon_kernel.c` 复刻其**内循环指令结构**：
同样的 3 载入 / 1 旋转 ALU / 2 存储、同样的 1024 元素与奇偶反向扫描，
保留 6 个 16 KiB 数组（96 KiB 足迹）。差异：

- 比对用显式 64-bit 扫描替代 libc `memcmp`，避免宿主 glibc 的 SVE 分派；
  读的是同样 16 KiB 的 dst。因此同时报告 `check=1`（完整）与 `check=0`
  （纯内核）两个变体。
- 不含 Sandstone 的 warm-up、线程绑核与失败种子搜索，不是功能级替代。

### 1.2 sdcfuzz 生成流

- `sdcfuzz-l1d-top3`：用 Phase 1 的 `structure_map.json` 对 `l1d` 排序，取
  前 3 条指令（实测为 `ldxr`、`ldr`、`str`），按 `OPS_PER_GROUP=4`、
  `GROUPS_PER_ITER=16` 组合成循环（`autousens target` 的候选形态）。
- `template-load-stream`：模板 `l1d-load-stream`，6 条 `ldr` 跨 6 条 cache
  line，16 组/迭代。
- `template-store-hot`：模板 `l1d-store-hot`，同址 `str` 重复。
- 追加 `sdcfuzz-l1d-top1`（`--top 1`，只有 `ldxr`）用于隔离实验。

所有流都跑 `--iterations 200`；内核 `--elements 1024 --sweeps 8`。

## 2. 测量方法

| 项 | 值 |
|---|---|
| gem5 | `CHAOS/gem5/build/ARM/gem5.opt`（原生 aarch64） |
| 配置 | `configs/se/arm_chaos.py --cpu=O3 --kp920_proxy` |
| 缓存 | L1I/L1D 64 KiB、L2 512 KiB、DDR3-1600 单通道 |
| O3 参数 | ROB 128、physInt 160、LQ 48、SQ 42、4-wide |
| 指标 | `--rf_ace --rf_ace_granularity=bit --l1_ace --fu_ibr --sad` |
| ROI | `m5_work_begin(7,0)` … `m5_work_end(7,0)` |

**归一化分母**：`sad.issuedOps` 不能用作分母——它统计每一次经过 IQ 发射
路径的尝试。top3 流实测 27,553 "issued" 对 3,894 条退休指令（7.1×），
因为 `ldxr` 与同址 `str` 冲突后被反复重选。因此 `tools/lsu_compare.py`
用 **N 与 N-1 两轮标定**求 ROI 内提交指令数：

```text
per_unit = simInsts_at_ROI_end(N) - simInsts_at_ROI_end(N-1)
ROI_insts = per_unit * N        # 预 ROI 的初始化开销相减抵消
```

这样既不需要重建 gem5，也不受发射重试影响；`iss/cmt` 列保留原始
`issuedOps` 与提交数之比，作为异常检测信号。

## 4. 解读

### 4.1 访存密度与 ACE 覆盖是两个目标

生成流把"每指令访存事件"推到 890–980/千指令，触发流只有 292；但 L1D ACE
覆盖率正好反过来：触发流 0.2204（纯内核 0.4106），生成流
0.0000015–0.0055。原因不是计数粒度，而是**空间局部性**：

- 生成流的缓冲固定 64 个 `uint64`（512 B），预热后全部命中，活跃 cache
  line 只有 8 条，line 生命周期被 12,800 次写快速终结（`lifetimeEnds`
  12,800），ACE 分子极小。
- 触发流 6 × 8 KiB = 96 KiB 在 64 KiB L1D 里轮转，每 sweep 重新触碰全部
  行，`trackedFills` 9,254、`lifetimeEnds` 41,352，线驻留时间被真实重用
  拉长，ACE 分子大。

因此 Phase 1 的 `l1d` 逐指令激活（demand 事件/指令）只能衡量"发了多少
访存"，不能衡量"多少 cache line 被持续激活"。要贴近 179 这类缺陷，生成器
需要把**工作集大小与重用距离**纳入目标，而不只是事件计数。

### 4.2 校验扫描会稀释 ACE

`core179-neon` 带每轮 16 KiB 的 dst 比对，ACE 0.2204；去掉后 0.4106。
校验扫描每 sweep 多出约 4,100 次读（2,048 个 64-bit 字 × dst/expected 两份），
把 dst 行反复顶掉，缩短了 srcA/srcB/scratch 的驻留。
这解释了原测试里"冷热交替"的访存形态：真实 ACE 覆盖介于两者之间。

### 4.3 RF ACE：触发流更高，但向量通道近乎失明

触发流 `RFint` 0.0826 高于所有生成流（0.0188–0.0550）：6 个数组的 3 载入
让整数地址寄存器与载入结果在 ROB/LQ 里驻留更久。

`RFvec` 只有 0.0013，尽管 ROI 内有 53,248 次向量读、34,816 次向量写。
当前向量 ACE 只跟踪 128-bit 寄存器的**低 64 位通道**，触发流的算术又是
128-bit 整型，指标既看不到高半，也覆盖不到长驻留向量寄存器。这是测量
盲区，不能据此判断硬件"向量寄存器不活跃"。

### 4.4 IBR：算术覆盖盲区

触发流 `IBRalu` 0.1929，看似很高，但分解后：145,998 条 intAlu 发射全部
是循环下标、分支与比对扫描；每元素 4 条 `add/eor/and/orr q`（8 sweeps ×
1024 × 4 = 32,768 条）不属于五类 FU 的任何一类，IBR 完全不计。

生成流的 IBR 更低（0.0063–0.0293），因为它们几乎只有循环控制。就"这条
触发流的算术主体"而言，IBR 目前给不出可比较的数字——需要补 SIMD 整型
（`SimdAdd`/`SimdAlu`）类，或按 op class 直方图报告未覆盖比例。

### 4.5 SAD：top3 的 LQ 打满是缺陷不是压力

`l1d-top3` 的 SAD lq 0.961、rob 0.563、iq 0.618，同时提交率只有 0.43
IPC；而访存全部命中（miss 率 1.02%）。隔离实验给出原因：

- 单独 `ldxr`：3.75 IPC、iss/cmt 1.002、LQ 正常。
- `ldxr` + 同址 `str`：提交被 LL/SC 监视器反复打断，发射重试 7.85×/指令。

`candidate_source()` 让所有探针共用同一个 `buffer` 指针，组合时没有别名
约束，于是把"独占载入 + 同址存储"这种语义上互斥的序列拼到了一起。这类流
不能作为 LSU 压力样本，也解释了为什么它的"高 LQ 占用"没有换来更高 ACE。

### 4.6 谁更接近 179 触发流

按维度拆开看：

| 维度 | 更接近触发流的是 | 说明 |
|---|---|---|
| 每指令访存密度 | 生成流（3.0–3.4×） | 纯 LSU 压力确实更强 |
| L1D ACE 覆盖 | 触发流（40–140000×） | 生成流缺工作集与重用距离 |
| RFint ACE | 触发流（1.5–4.4×） | 长驻留载入结果 |
| RFvec ACE | 都不可用 | 64-bit 通道 + 无 128-bit 语义 |
| IBR（算术） | 都不可用 | SIMD 整型不在五类 |
| 提交效率 | 模板流接近（3.3–3.7 IPC） | top3 流是病态 |

结论：现有 sdcfuzz 生成器能造出**高访存密度、低 ACE 覆盖**的流；179 触发
流恰好相反——访存密度中等，但 cache line 与寄存器驻留时间长。两者不是
"谁更强"，而是优化目标不同。

## 5. 对生成器的具体建议（Phase 2 输入）

1. **别名约束**：组合探针时禁止 `ldxr`/`ldaxr` 与同地址 `str` 同流；或给
   每条探针独立基址。当前 top-k 组合会自造 LL/SC 重试。
2. **工作集与重用距离入目标**：`l1d` 目标从"事件/指令"改为
   "ACE 覆盖 + 足迹/重用距离"，例如给候选加 `--footprint` 参数，
   在 8 KiB–256 KiB 间扫描。
3. **读写比可配置**：触发流是 3:2（含 scratch 的 3 载入、2 存储）。现有
   模板只能全读或全写。
4. **向量访存与向量 ALU**：补 `ldr q`/`str q` 探针，以及 SIMD 整型 IBR 类，
   否则 128-bit 触发流无法被表达、也无法被度量。
5. **报告口径**：把 `issuedOps`（含重试）与提交数分开；本次已用 N/N-1 标定
   兜底，长期应在 SAD 里加 ROI 内提交计数。

## 6. 局限

- 复刻的是指令结构，不是 OpenDCDiag 二进制；warm-up、绑核、失败种子
  搜索不在范围内。
- `--kp920_proxy` 是 V110 代理模型，非 cycle-accurate；SAD/ACE 的绝对值
  只在同配置内可比。
- 生成流比触发流短 1–2 个数量级（3.6k–38.8k vs 194k–309k ROI 指令）；
  比率已归一化，但 SAD 占用对短流更敏感（store-hot 仅 1,079 采样周期）。
- gem5 不支持 SVE；触发流本身也不用 SVE，不影响本次对比。
