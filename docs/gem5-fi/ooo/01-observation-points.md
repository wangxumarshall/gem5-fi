# 01 · 观测点定义（L0~L4 传播链监控）

> 来源：工作表「2.观测点定义」R1–R6，内容忠实提取（L1/L2 的多行采集量按源表内换行拆为条目）。
> 所有单元、所有实验格（E001–E226）共用这一套层级定义；设计矩阵的「L1 重点观测点」列
> 是 L1 层在每个具体注入位置上的定制化。

## 层级总表

| 层级 | 名称 | 定义（原文） | 适用范围 |
|---|---|---|---|
| L0 | 注入点生命周期 | 被注入的那一项/那个字段，在被覆盖或运行结束前，有没有被后续逻辑真正读取过。 | 全部单元通用 |
| L1 | 微架构内部偏差 | 在故障传播到 commit 之前，微架构内部状态相对「无故障影子副本」的分歧。是本方案回答「SDC 前期有什么特征」的核心层——多数论文只看 L2/L4，这一层是本方案区别于现有文献的重点。 | 全部单元，字段按单元定制 |
| L2 | 架构可见点（commit 处） | 沿用 TC'23 的方法论：在 commit 阶段逐条比对提交指令的 PC、opcode、寄存器操作数/立即数、寄存器内容，与无故障参照运行比对，归入五类之一。 | 全部单元通用（TC'23 原始定义） |
| L3 | 软件层传播 | 架构可见的分歧，继续在软件执行中扩散的路径与范围。 | 全部单元通用，SIMD 专属字段仅用于 FP/SIMD 三个单元 |
| L4 | 最终结局 | 沿用统一口径：Masked / SDC / Crash / Timeout。Crash 进一步拆分「仿真器断言崩溃」（依赖检查失败等 gem5 内部检查触发）与「架构崩溃」（非法指令、段错误等传到软件层的崩溃），因为①里说明的依赖检查机制会让很大一部分「本该是 SDC」的故障被计成仿真器断言崩溃，这个拆分是判断某个位置「真实 SDC 潜力」的关键，不能和真机可能出现的架构崩溃混在一起看。 | 全部单元通用 |

## 各层典型采集量（原文）

**L0 注入点生命周期**
- 命中/未命中标记；若未命中，直接归入「无效注入」，不计入 SDC 统计分母（这是统计口径问题，不是故障效果）。

**L1 微架构内部偏差**（按单元定制）
- Rename：影子 RAT 与实际 RAT 的分歧项数、Free List 实际占用与期望占用的偏差、rename 阶段停顿周期数、WAW/WAR 冲突计数。
- Dispatch/ROB：ROB 头/尾指针偏差、commit 阶段停滞周期数、flush 次数、IQ ready 位分歧数。
- Decode：非法指令/非法寄存器号异常计数、IPC 偏差、squash 次数。
- 全单元通用：IPC 相对无故障基线的偏差（借鉴 CHAOS 论文用 HPC 计数器偏差捕捉「未崩溃但已严重偏离」的做法）。

**L2 架构可见点（commit 处）**
- 五类：①执行时间错（Execution Time Error）②指令流改变（Instruction Flow Change）③指令替换（Instruction Replacement）④操作数强制切换（Operand Forced Switch）⑤数据损坏（Data Corruption）。
- 额外记录：首次出现分歧的 commit 序号（潜伏期，用「提交指令数」而不是时间，因为故障会改变时序）。

**L3 软件层传播**
- 污染是否到达：地址计算 / 分支条件 / store 数据；污染的物理寄存器被后续几条指令读取（扇出计数）；
- SIMD/向量场景额外记录：污染是否只影响部分 lane 还是整个寄存器。

**L4 最终结局**
- 四类计数 + 仿真器断言崩溃占比；额外标记「Masked 或 SDC，但 L1 阶段 IPC/计数器偏差超过阈值（建议 >50%）」的隐蔽样本，单独统计占比——这类样本是「表面无事、内部已经跑偏」的候选，值得优先深挖传播路径。
- **Crash 双拆分（原文）**：Crash 进一步拆分「仿真器断言崩溃」（依赖检查失败等 gem5 内部检查触发）与「架构崩溃」（非法指令、段错误等传到软件层的崩溃），因为①里说明的依赖检查机制会让很大一部分「本该是 SDC」的故障被计成仿真器断言崩溃，这个拆分是判断某个位置「真实 SDC 潜力」的关键，不能和真机可能出现的架构崩溃混在一起看。
