## 重要边界条件（贯穿全篇的设计前提，务必先读）

① gem5 的 O3CPU 对 ROB/RAT 相关字段有依赖图检查（dependence graph check）：TC'23 论文证实，随机翻转 ROB 的 PC / 寄存器标识符字段，几乎全部在 commit 前触发依赖检查失败 → 直接 Crash，SDC 概率量出来是 0%（Armv7、Armv8 都是 0%）。这是本方案设计「换值」类结构化模型的直接动机——随机翻转会被这道检查拦下来，要绕开它，必须让翻转后的值仍然「合法」（比如映射到另一个正在使用的物理寄存器号），这样依赖检查会通过，故障才有机会真正传播到架构状态。

② Veritas 论文（HPCA'25）对「控制逻辑」（指令译码、调度等）的论断是：持久故障「非常不可能」导致 SDC，通常严重破坏控制流直接崩溃。这条论断没有配实验，本方案的译码/发射相关行，就是用来检验这条论断在结构化故障模型下是否依然成立。

③ 到本方案设计之时为止，没有任何一篇已发表论文对 Int Rename、Int Dispatch 的分发/发射逻辑本身（不含 ROB 字段）、FP/SIMD Rename、FP/SIMD Dispatch 做过故障注入实验（见《OoO单元参数总表.md》里逐单元核对的「无」）。这六个单元里，只有 Int Dispatch/ROB 的 ROB 字段（TC'23）和 Int Decode 的时延故障（MICRO'24 DelayAVF，且是别的核、别的故障模型）有直接对照数据，其余全部是空白，本方案是目前已知第一份系统覆盖这六个单元的注入设计。

④ CHAOS 论文（gem5 RISC-V O3）的实测规律：注入概率越高，结果越集中在 Crash；注入概率越低，SDC / Masked / Timeout 占比越高。本方案的频率档位设计直接借用这个规律：先用少量试跑找到「非 Crash 占比」最高的频率区间，再在那个区间做正式统计量的实验，而不是均匀地在所有频率上平均分配算力。

⑤ 除 fetchWidth/decodeWidth=4 外，本方案用到的所有 gem5 结构容量数字（ROB=128、IQ=64、PRF=128/192/48 等）均不是鲲鹏 920 的真实规格，是 Cortex-A72 公开资料 + gem5 官方 ARM 示例配置拼出来的估计值，写论文必须原样注明来源，不能当 920 真值用。
