# gem5-fi ARM64 SDC 故障注入源码检查报告

## 一、先说结论

这次检查的代码是 `gem5-fi` 仓库的 `fi` 分支：

- 当前提交：`70b725ca5c18df735ee64dff1b492ecbac603698`
- 内置 gem5 版本：v25.1.0.1
- 检查日期：2026-08-26

最直接的结论是：

> **ARM64 故障注入的基本框架已经搭起来了，但工具还没有做到可以正式开展大规模实验。现在得到的结果只能算初步现象，不能直接当作 ARM64 或鲲鹏处理器的 SDC 规律。**

目前已经有寄存器、缓存和内存等故障注入代码，也准备了测试程序和自动运行脚本。但源码中仍有几处会直接影响实验结果的问题，包括永久故障失效、高位寄存器故障没有真正注入、NEON 代码可能越界，以及实验脚本可能把运行错误误判成 SDC 或 Hang。

因此，现阶段最重要的工作不是继续扩大实验数量，而是先把工具修正确认。

## 二、现在已经做了什么

### 1. 搭建了 ARM64 gem5 实验环境

仓库中已经加入：

- ARM64 SE 模式配置；
- O3 处理器模型；
- L1I、L1D 和 L2 缓存配置；
- ARM64 测试程序；
- 故障注入参数和运行脚本。

这些内容说明，ARM64 故障注入实验的基本环境已经形成。

### 2. 已经加入的故障注入位置

目前源码中可以看到以下注入模块：

| 注入位置 | 当前情况 |
|---|---|
| ARM64 通用寄存器 | 已有基本注入功能 |
| O3 物理寄存器 | 已有基本代码，但位宽和永久故障仍有问题 |
| L1I、L1D、L2 数据 | 已有随机数据字节翻转功能 |
| 内存 | 已有单字节故障注入功能 |
| 浮点/向量寄存器 | 加入了初步代码，但现在不能安全使用 |
| LSQ 前递数据 | 加入了初步接口，还没有接入正式实验 |
| TLB、系统寄存器 | 尚未实现 |
| 鲲鹏 920 的 128 B L3、ECC/RAS | 尚未实现 |

### 3. 加入了实验控制功能

部分模块已经支持：

- 设置随机种子；
- 限制一次实验只注入一个故障；
- 记录部分故障信息；
- 使用 manifest 描述实验参数；
- 根据程序输出判断故障是否影响结果。

这些工作方向是正确的，但目前不同模块的实现不统一，日志和结果分类也不够可靠。

## 三、现在做得怎么样

总体上，可以把当前版本看成一个“可以继续开发和调试的原型”，还不能看成“已经验证完成的实验工具”。

### 做得比较好的部分

1. **ARM64 基本实验环境已经建立。**

   配置文件、测试程序和注入模块已经放在同一仓库中，后续可以在这个基础上继续修改。

2. **缓存访问方式得到改进。**

   当前实际构建源码使用 gem5 提供的公开接口访问 classic cache，删除了原来不安全的强制类型转换。这一部分基本符合设计方向。

3. **通用寄存器的架构态注入已经扩展到 64 位。**

   `CHAOSReg` 可以表达 64 位寄存器掩码，也加入了随机种子和单故障限制。

4. **内存故障类型的概率和部分地址边界问题已经修过。**

   这些修改说明开发过程已经开始关注故障是否真正按预期注入，而不是只关注程序能否运行。

### 仍然存在的主要问题

#### 1. 永久故障目前并不永久

之前的一个提交曾加入“寄存器以后每次被写入时，都重新施加 stuck-at 故障”的代码。但这部分在后续合并中被覆盖了。

当前代码只重新修改一次寄存器，随后把更新标志设为 `false`。程序之后再次写这个物理寄存器时，故障可能消失。

所以，当前版本不能用来研究真正的永久故障。

#### 2. 物理寄存器只能可靠注入低 32 位

架构态寄存器模块已经扩展到 64 位，但 P0 实验实际使用的物理寄存器模块仍然使用 32 位故障掩码：

- `faultMask` 还是 `UInt32`；
- C++ 中还是 `bitset<32>`；
- 随机掩码也只生成 32 位。

但是测试脚本又尝试注入 bit 32 和 bit 63。这两个值超出了 `UInt32` 的范围，配置可能在真正开始模拟前就失败了。

因此，之前报告中“高位故障更容易导致 Hang”的结论不能成立。

#### 3. NEON/向量寄存器代码存在越界风险

当前代码只准备了 64 B 的临时缓冲区，但 ARM gem5 的向量物理寄存器最大为 256 B。读取向量寄存器时，可能把 256 B 数据写入 64 B 空间，造成内存越界。

这不仅会影响实验结果，还可能让 gem5 自身崩溃。因此，在修复前必须关闭向量寄存器注入，不能用它研究 NEON。

#### 4. 实验结果可能被错误分类

统一运行脚本目前没有正确使用程序退出码。

例如：程序已经异常退出，输出也不正确，但只要日志中记录了一次注入，脚本仍可能把它判成 SDC。实际做了一个简单验证，结果如下：

```text
程序退出码 = 1
输出为空
故障注入次数 = 1
脚本分类结果 = SDC
```

这种情况应该先判断是配置错误、模拟器错误还是程序崩溃，而不能直接算作 SDC。

其他测试脚本也有类似问题：

- 没有输出就直接算 Hang；
- 没有检查程序退出码；
- 没有确认是否真的只注入了一次；
- 日志解析失败后仍然返回成功；
- 没有严格使用 manifest 中指定的寄存器、位号和触发位置。

所以，目前统计出的 SDC、Hang 和 Masked 数量不够可信。


#### 5. 仓库中存在两份不同的源码

顶层 `CHAOS/CHAOSReg`、`CHAOS/CHAOSCache`、`CHAOS/CHAOSMem` 和实际参与构建的 `CHAOS/gem5/src/` 内容不同。

Makefile 会把顶层代码复制到 gem5 源码目录。如果使用旧副本构建，已经修过的问题可能再次被覆盖。

后续应确定唯一的一份正式源码，避免“修改了一个目录，实际编译的是另一个目录”。

## 四、原计划完成到了什么程度

原计划设置了 G0—G7 七个基本检查。根据当前源码，实际情况如下：

| 检查项 | 当前状态 | 直白说明 |
|---|---|---|
| G0 随机结果可重复 | 部分完成 | 寄存器做过重放，其他模块没有完整验证 |
| G1 位宽和目标合法 | 未完成 | 架构态寄存器是 64 位，但物理寄存器仍是 32 位 |
| G2 永久故障语义 | 未完成 | 正确实现曾经存在，但合并后丢失 |
| G3 缓存安全访问 | 基本完成 | 只适用于当前 classic cache 数据区 |
| G4 内存注入正确性 | 部分完成 | 修了概率和部分边界，但代码和测试仍有问题 |
| G5 一次只注入一个故障 | 部分完成 | 有次数限制，但计数和日志不完全可靠 |
| G6 注入触发位置 | 部分完成 | 只能按简单时间触发，没有完整的指令、PC 和 ROI 触发 |
| G7 工具自身不能出错 | 未完成 | 当前版本未重新构建，向量代码还有越界风险 |

所以，`progress.md` 中“G0—G7 已经全部完成”的说法和当前源码不一致。

## 五、目前发现了什么现象和规律

### 可以暂时保留的初步现象

#### 1. 关键整数寄存器发生低位翻转，可能造成 SDC

之前的实验中，X2 和 X3 的低位发生翻转后，程序最终校验值发生变化。这说明：如果故障打到仍会被后续指令使用的关键寄存器，错误可能沿数据依赖传播到最终输出。

这个现象在原理上是合理的，也值得继续验证。但由于当前代码经过合并、脚本分类又有问题，需要修复后重新运行，暂时不能计算 SDC 概率。

#### 2. 随机 L1D 故障经常没有影响程序结果

之前的 L1D 小规模实验中，多次注入都没有改变输出。

这并不一定说明 L1D 不敏感，更可能是：

- 故障没有打到程序真正使用的数据；
- 数据在被使用前已经被覆盖；
- 故障所在 cache line 被替换；
- 程序没有再次读取被修改的字节。

因此，目前只能说“随机 L1D 数据故障容易被掩蔽”，不能说“L1D 的 SDC 风险低”。

#### 3. L1I 故障可能更容易破坏程序控制流

之前的 L1I 实验表现为程序长时间不结束。这与指令被破坏后出现错误跳转、死循环或异常指令的可能性一致。

但当前脚本会把配置错误、程序崩溃和真正超时都算成 Hang，所以“L1I 10 次全部 Hang”还不能确认。

更准确的表述是：

> L1I 故障可能比随机 L1D 数据故障更容易影响程序控制流，但需要重新区分 Hang、Crash 和模拟器错误。

### 目前不能保留的结论

以下结论现在没有足够证据：

- bit 32 和 bit 63 的故障更容易造成 Hang；
- ARM64 通用寄存器的 SDC 率是 20%；
- L1D 故障一定全部被掩蔽；
- L1I 故障一定全部导致 Hang；
- ARM64 或鲲鹏比 x86 更容易发生 SDC；
- NEON、LSQ、TLB、系统寄存器和 128 B L3 的敏感性高低；
- 当前结果可以代表鲲鹏 920 实机。

目前最大的规律其实是：

> **如果不能确认故障确实打到了指定位置，也不能正确区分程序错误、模拟器错误、Hang 和 SDC，那么增加实验次数也不会得到可信结论。**

## 六、接下来应该怎么做

建议按照下面的顺序继续：

### 第一步：先修工具

1. 恢复真正的永久故障写入钳位。
2. 把物理寄存器故障掩码扩展到 64 位。
3. 暂时关闭 NEON 注入，先修复向量缓冲区越界。
4. 修正 SDC、Hang、Crash 和工具错误的分类逻辑。
5. 让 manifest 中指定的寄存器、位号和触发位置真正生效。
6. 统一源码目录，避免 Makefile 用旧代码覆盖新代码。

### 第二步：重新构建和验证

在 ARM64 Linux 环境中，对当前最终提交进行一次干净构建，然后重新检查 G0—G7。

每次实验必须保留：

- 当前 Git 提交；
- 完整运行命令；
- 实际注入的位置和位号；
- 故障前后的值；
- 程序退出码；
- 标准输出和错误输出；
- 故障日志和 gem5 统计文件；
- 最终分类及分类原因。

### 第三步：重新运行最小实验

先不要马上做几百次实验，只重跑最容易验证的几组：

1. X2、X3 的 bit 0、31、32、63；
2. 固定到程序正在使用的数据上的 L1D 故障；
3. 固定到实际执行指令上的 L1I 故障；
4. 内存首地址、末地址和单字节范围故障。

确认每组实验都能稳定重放、分类正确后，再扩大样本量。

### 第四步：再扩展 ARM64 特有单元

建议依次开展：

1. 128 位 NEON 寄存器；
2. LSQ store-to-load forwarding；
3. TLB 和系统寄存器；
4. 鲲鹏 920 的 128 B L3、ECC 和 RAS；
5. x86 和 ARM64 的同条件对比；
6. 鲲鹏实机验证。

## 七、最终评价

当前版本已经完成了 ARM64 SDC 故障注入工具的基本框架，说明整体技术路线可以继续推进。

但是，它现在仍处于开发和验证阶段。永久故障、64 位物理寄存器、NEON、结果分类和实验留痕等关键问题还没有解决，所以不能直接用于正式的 SDC 统计实验。

目前能够汇报的成果是：

- ARM64 gem5 故障注入环境已经搭建；
- 寄存器、缓存和内存的基本注入路径已经加入；
- 观察到寄存器低位错误可能传播到最终结果、L1D 随机错误容易被掩蔽、L1I 错误可能影响控制流等初步现象；
- 通过源码检查发现了会影响实验可信度的关键问题，并明确了后续修复顺序。

目前不能汇报为正式结论的是：

- ARM64 或鲲鹏的 SDC 敏感性规律；
- ARM64 与 x86 的敏感性差异；
- 各单元的 SDC 率、AVF 或风险排序。

一句话总结：

> **工具的架子已经搭起来了，也看到了一些值得继续验证的现象；但工具本身还要先修正，之后重新实验，才能得到可信的 ARM64 和鲲鹏 SDC 规律。**

本次检查和改写没有修改下载仓库中的源码。
