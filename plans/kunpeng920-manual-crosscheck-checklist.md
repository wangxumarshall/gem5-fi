## A. 保护 / 校验 / 纠错清单（最高优先——直接决定 category-2 能不能从"猜"变"实锤"）

对每一项确认：**有没有保护 → 类型（parity 纯检出 / SECDED / DECTED / 冗余比对 / 无）→ 保护粒度 → 检出后的动作（丢弃重算 / 流水线冲刷重放 / 静默纠正继续跑）**。

- [ ] **PRF 物理寄存器堆**（整数堆、浮点/向量堆分开确认）——是否有 parity 或 ECC？两者策略是否不同？
- [ ] **RAT 重命名映射表**——条目（存的是物理寄存器编号）是否有 parity？
- [ ] **FreeList 空闲列表**——空闲位图/列表结构是否有保护？
- [ ] **ROB 条目**——状态位（可提交位等控制位）和 payload（数据）是否分开考虑保护？
- [ ] **IQ 发射队列**——payload 缓冲、唤醒用的 tag 比较阵列是否有 parity？
- [ ] **LSQFwd 存储-加载转发通路** / **L1DForward（L1D 未命中回填、ECC 校验之后到写寄存器之前这一段）**——这两段是不是天然处于"校验之后"的保护盲区？（这是我们报告里 §9/§10 静默率 32–95%/90.9% 的核心假设，务必确认或证伪）
- [ ] **SysReg 系统控制寄存器**（SCTLR / TTBR0-1 / TCR 等）——普通触发器还是有奇偶/冗余？关键寄存器是否有特殊保护？
- [ ] **L3 tag / 一致性目录**——tag 阵列本身是否有 parity？（注意区分：我们注入的"tag 换成合法别名"是逻辑错误，parity 只防存储阵列位翻转，防不住这类逻辑错误——手册最好能讲清楚这两者的边界）
- [ ] **L1D / L1I / L2 的 tag 阵列**（区别于 data 阵列，我们现在的 SECDED 结论全部是 data 阵列的，tag 阵列独立保护完全没测过）——是否有独立保护？
- [ ] **PTW 页表项路径**——现在标"已知有保护"，需要确认：这个 ECC 是页表项走 L1D/L2/DRAM 数据通路时继承的 ECC，还是 PTW/TLB 有独立一层保护？（决定 §20 H7 结论怎么写）
- [ ] **数据 TLB 层级结构**——真实芯片是几级？（我们目前只建模了一层"数据TLB"，大概率实际是 L1 DTLB + L1 ITLB + L2 统一 TLB，甚至有独立 Page Walk Cache——如果有，这是覆盖度缺口，见 B 部分）

## B. 覆盖完整性核对（拿手册流水线框图逐项对我们的 23 个单元）

- [ ] **TLB 层级**（同 A 部分）——是否遗漏了 L2 TLB / STLB 层级？
- [ ] **Page Walk Cache（PWC）**——介于 TLB 和真正走页表之间的缓存，我们完全没建模，是否存在？
- [ ] **Store Buffer / 写合并缓冲**——是否独立于 LSQ、需要单独建一个注入单元？
- [ ] **μop cache / loop buffer**——V110 是否有，我们完全没测。
- [ ] **预取器（L1/L2 stream prefetcher）**——预取器出错通常只影响性能不影响正确性，但请手册确认这个假设。
- [ ] **ROB / IQ / PRF 真实容量**——校准我们假设的 ROB=128 默认值、"ROB=160 危险区"结论用的参数是否真对上 V110（而不是套用通用乱序处理器参数）。
- [ ] **发射端口数量和类型**（几个整数 ALU、几个 AGU、几个 FPU/SIMD 端口）——决定 Exec/FPU 注入器打的"结果通路"是否代表了全部执行端口。
- [ ] **是否存在其它我们完全没意识到的流水线部件**（框图逐项过一遍，看有没有遗漏的功能块）。

## C. RAS 告警链路（校准我们"SDC = RAS 全程零告警"这个核心定义）

- [ ] **鲲鹏920的 RAS 实现拓扑**——ARM v8.2-RAS 扩展的 ERR 记录寄存器、SError 路由、是否对接 GHES/BERT（ACPI）、SEL（BMC 侧）——完整链路长什么样？
- [ ] **关键问题**：那 4 个"真有保护"的单元（L1D/L1I/L2/DRAM 的 cache/mem ECC、DTLB、PTW）检出并纠正一个错误时，**会不会产生一条 RAS 日志（CE 记录）**？如果纠正是完全静默无日志的，那我们现在划进"C2 过程中被检出"的部分，从系统可观测性角度其实也是零告警——可能需要把 C2 再细分成"检出纠正但无日志" vs "检出纠正且有日志"两档。
- [ ] **Poison bit 机制**——不可纠错误是否会给缓存行打 poison 标记、推迟到消费者读取时才报错？（对应我们 L2/DRAM 注入器 `bits_to_change≥3` 的 SilentEscape 分支，确认建模是否画对了）
- [ ] **哪些我们分类为"C3(3b 崩溃暴露)"的场景在真机上会真的产生 SError / panic，哪些可能压根不 trap**——尤其是 exec = C2 平台"全部转崩溃暴露"这类结论，需要确认真机是否也有等价的边界检查。
