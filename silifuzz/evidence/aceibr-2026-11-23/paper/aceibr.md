# 指令流 vs 模板：ACE / IBR 结构指标（gem5 O3 + kp920 proxy）

生成时间 2026-11-23 19:07　数据：`work/paper-20261123`（20 个模板各一条流）

## 口径（先读这一节，否则数字会被误读）

1. **窗口**：`m5_work_begin(7,0)` → `m5_work_end(7,0)`。两侧各跑约 6 万条动态指令（块长 × 迭代），同迭代数的空块基线相减后归一化。
2. **两侧唯一变量是指令序列**：寄存器初态约定完全相同（x0–x29 指向 64 MiB 零页、4 KiB 步长；d0–d7 = 1.0/2.0/0.5/−1.0/3.0/1e−8/1e8/1+1e−7）。
3. **ACE**（本仓库 rfAce/l1Ace 模型）= 物理寄存器堆与 L1 中被访问值的**生命周期占用**：`intAceRatio = ACE bit-cycles / (物理寄存器数 × 位宽 × 窗口周期数)`。下表三项都是**扣除空块基线后**属于指令块的份额：「RF 条目」= `ΔregCycles / 窗口周期数`（平均被覆盖的物理寄存器条目数）；「RF ACE(净)」= 模型比例 × `ΔbitCycles / bitCycles`（分母常数不可见，用份额缩放）；「L1D 行」= `ΔlineCycles / 窗口周期数`（平均被覆盖的 cache line 数）。「RF 访问/1k」是模型计数的寄存器读写事件/千条块内指令，不是指令条数。
4. **IBR**（fuIbr 模型）= `ports[FU] × 操作数位宽`，即**每条发射指令的结构性输入端口位宽**，不是数据相关的翻转率：intAlu/intMult 为 2/3 个 64 位源 → 128/192 bits，标量 fpAdd/fpMult 为 2×32 或 2×64。因此 IBR 的判别力在**单元占用分布**（表 2），`bits/op` 只反映 32/64 位与 2/3 源的比例。
5. **指令归一化**（逐条明细见 `guests.json`）：控制流/特权/写 SP → `b .+4`（保留分支端口占用，不转成 intAlu）；访存基址 → x19（数据窗口），使长访存流可测；仍在宿主上触发故障的个别字按位剔除并记录。

## 读法与观察

- **覆盖率不是长度**：两侧 ROI 指令数相同，所以 RF 条目 / L1D 行的差异来自「每条指令碰到多少个不同结构」，不是「跑了多久」。
- **寄存器堆：0/20 的流覆盖更多条目**（）；下降的只有 c1, c3, e1, e2, e3, f1, i1, i2, l1, l2, m1, m3, o1, o2, v1, v2, v3, v4, v5, v6。
- **L1 侧同向**：0/20 的流覆盖更多 cache line，0/20 的 L1D ACE(净)更高；两者几乎完全一致，说明「结构占用」与「时间占用」在本实验里没有分叉。
- **v4 是唯一反向的例子**：寄存器条目 11.2→7.6 下降而 L1D 行 7.0→8.7 上升——它的流有 73 条访存基址被改写到 x19，访存变多、寄存器写变少。这正说明两个指标必须分开看：ACE 不是单一分数。
- **IBR bits/op 只有 4/20 上升**：该值 = `ports × 位宽`，流里 32 位或单源指令比例一变它就变，`128.0` 说明两侧都以 2 源 64 位整数运算为主。**判别力在表 2 的单元占用分布**：多数模板流的 intAlu 每千条占比下降，因为流里掺入了访存/向量/分支占位指令。
- **c1 / v5 只有 1 条指令**（gap 模板）：RF 条目 3.0→0.0 / 33.1→0.0，IBR 128→64.4 / 128→106.7。这是单指令与 26/42 条模板的结构差异，不能读成「流更差」——它们本来就没被交付为可用流。
- **e1 有 38%（69/180）的编码被宿主反汇编器判为未分配**：该流来自 Capstone 语料（字节级变异），此前按「可解码指令」算的纯度 0.80 并不覆盖这 38%%。这些字已按未分配剔除，其 ACE/IBR 只反映剩余 111 条有效指令。
