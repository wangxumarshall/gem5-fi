# sdcfuzz 模板 ↔ SiliFuzz 指令流配对（2026-11-23）

本文记录 `silifuzz/tools/pairgen.py` 的第一次完整运行：为 `sdcfuzz/upstream/seeds/`
下的 **20 个** 微架构模板各生成 **1 条 SiliFuzz 指令流**，并让每条流走完
`ifuzz → sf_fix → sf_player → sf_checker → fleet` 全流水线。

产物（受版本管理，不是临时目录）：[`../evidence/pairs-2026-11-23/`](../evidence/pairs-2026-11-23/)

- `manifest.json` —— 逐配对的全量事实：模板哈希、候选哈希、快照哈希、类分布、
  JS 散度、执行深度、修复/回放/机群统计、生成器二进制哈希。
- `pairs.md` —— 人读表格（配对表、机群校验、逐模板候选统计）。
- `snapshots/<id>.sfs` —— 20 个快照，文件名即模板号。
- `wordlists/<id>.txt` —— 每个模板实际可用的、已逐字校验的「编码字 + 类名」清单。
- `checks.json` —— 128 核 sweep / 50-1000 采样 / 4 核窗口的原始摘要。

## 1. 判定口径：编码类，而不是助记符

配对不能按 objdump 助记符做：同一段机器码，objdump 会把 `MOVZ` 显示成 `mov`、
`SUBS` 显示成 `cmp`、`UBFM` 显示成 `lsl`。按文本匹配会得到"看起来覆盖、实际不同类"
的伪对应。

因此契约定义在 **ifuzz 自己的解码结果**上：把模板汇编成 `.o`，逐条 32-bit 字送进
`arm64.ParseInsn`，得到类名（如 `MOV (wide immediate)`、`SUBS (shifted register)`）。
流侧用同一解码器复查。一个配对算成立的条件是：

1. 模板出现的每个编码类都在流里至少出现一次（覆盖率 1.0）；
2. 流里不出现模板之外的类；
3. 流长度与模板同量级，类分布用 Jensen-Shannon 散度量化（不设阈值，如实报告）。

## 2. 生成器：四个可选开关，默认路径不变

上游 syzkaller 的 ifuzz arm64 用户态表（1212 条）不覆盖本项目的三个需求，
`tools/ifuzzgen` 因此增加了**全部默认关闭**的扩展：

| 开关 | 解决的问题 | 依据 |
| --- | --- | --- |
| `-lse` | 上游表没有 CAS/SWP/LDADD 等 ARMv8.1 原子指令（v5 模板的核心） | 17 条编码由系统汇编器产出后再反汇编回读 |
| `-branch-ext` | 上游 B/B.cond/CBZ/TBZ 的固定位移全是 0，等于自跳转死循环，`sf_fix` 只能按 timeout 拒绝 | 14 条前向位移编码，掩码沿用上游表 |
| `-vec-ext` | 上游 `DUP (element)`/`MOV (to general)` 的 imm5=0 是未分配编码（执行即 SIGILL） | 4 条合法 imm5 编码 |
| `-words` | `-opcodes` 只能保留表内已有条目，外部校验过的寄存器变体不是表项，会被静默丢弃 | 直接以「编码字 + 类名」清单为指令集 |
| `-balance-classes` | 表内条目多的类会被采样淹没（`MOVK` 条目远多于原子类） | 先等概率抽类，再类内抽编码 |

未加任一开关时，注册的指令集与上游逐字节一致（1212 条），此前 95k / 505k 语料的
可复现性不受影响。

## 3. 上游表的两个缺陷与处理

运行中发现两类问题，都属上游表状态，不是本流程引入：

1. **未分配编码**：如 32 位 `ADD/SUB (shifted register)` 配 ROR 移位、`DUP` 的 imm5=0。
   执行即 SIGILL。
2. **字段表错位**：部分条目把 `Rm` 标在 bit20（正确是 bit16），按字段写寄存器会
   踩坏 `shift` 位，生成出非法编码。

处理方式：变体构造放在 `pairgen.py` 里逐字校验 —— 每个候选词必须
(a) 仍被 `ParseInsn` 分类为该类，(b) 被系统反汇编器判为已分配。20 个模板合计保留
**1712** 条可用编码，剔除 **1672** 条"分类漂移"与 **77** 条未分配编码；
逐模板数字见 `manifest.json` 的 `variant_stats`。

寄存器策略：`Rn` 只从 **x18–x25** 取，且没有任何指令写这 8 个寄存器；其余寄存器字段
从 x0–x17/x26–x28 取。这与 sdcfuzz 用 x6/x7 固定数据基址的约定同源，保证流里的
访存都落在映射窗口内，而不是在上游表"全部寄存器都写 x0"的退化形态下第二三条就缺页。

## 4. 流水线与验收断言

| 步骤 | 命令主体 | 验收断言 |
| --- | --- | --- |
| 契约 | `gcc -c` + `ifuzzgen -classify` | 模板指令 100% 落在 ifuzz 词汇表内 |
| 词表 | `pairgen.py analyze` | 每词合法且分类不变；空类直接报错退出 |
| 生成 | `ifuzzgen -words -balance-classes` | 候选全部指令合法 + 类覆盖 100% |
| 修复 | `sf_fix --centered-data --data-pages 16 --ref-cores 0,32,64,96 --repeat 3` | 端态 PC **正好落在末尾 BRK**，即整条流执行完 |
| 审计 | `sfsnapshot.load` + `ParseInsn` | 快照代码段逐字节等于被选候选；覆盖率重算为 1.0 |
| 回放 | `sf_player --core {0,32,64,96} --repeat 3` | 12 次回放全部 `match:true` |
| 机群 | `sf_checker --cores 0-127`、`fleet.py --window-cores 4` | 不匹配 0、错误 0 |

"执行深度"这一步是本轮加的关键闸门。初版只按静态指标选候选，结果 c1 在第三条指令
就被 `eor x0,x0,x0` 清零后 `ldr [x0]` 打死，v4/v6 第一条就是 SIGILL —— 快照本身确定、
可回放，但整条流没被执行，属半成品。现在批量修复 **3815** 个候选，只保留
**2817** 个跑到末尾的，其余 **998** 个（中途异常终止或越过末尾落入填充区）全部丢弃换候选。

## 5. 结果摘要

- 20/20 配对成立：类覆盖率 1.0，流长 786 条 vs 模板 733 条（长度比 1.00–1.24），
  JS 散度 0.0026–0.219。
- 快照全部以 `SIGTRAP`（末尾 `BRK`）结束，`pc_offset == code_bytes`。
- 128 核 sweep：20 快照 × 128 核 = 2560 次执行，0 不匹配、0 错误。
- 128 核 50/1000 采样：30 s 内 764,152 次执行（25.4k/s），0 不匹配。
- 4 核窗口：2 个窗口 × 60 s，160 次执行，0 不匹配。

完整表格见 [`../evidence/pairs-2026-11-23/pairs.md`](../evidence/pairs-2026-11-23/pairs.md)。

## 6. 边界

- 对应关系是**编码类**层面：同类内寄存器/立即数取值不同。这是 ifuzz 固定操作数模板
  决定的，也是 SiliFuzz「覆盖无关生成」与 sdcfuzz「定向模板」的本质差异；本文不声称
  操作数级等价。
- 分支类流可能跳过尾部若干指令（前向跳转直接落到 BRK）；执行完整性由端态 PC 判定，
  不是逐指令轨迹。
- 流为单线程快照回放；跨核一致性压力由机群窗口的多核并行提供，与 sdcfuzz 模板注释里
  "真多核由 orchestrator 触发"的说法一致。
- JS 散度只作描述，不作阈值：i1（81 条 NOP/ALU 交替）散度最高 0.219，因为模板里
  NOP 与 ALU 的比例是写死的，而 ifuzz 按类等概率抽样。

## 7. 复现

```bash
cd silifuzz
python3 tools/pairgen.py analyze  --work work/pairs-20261123 --variants 8 --seed 1
python3 tools/pairgen.py generate --work work/pairs-20261123 --n 400 --keep 200 --seed 1
python3 tools/pairgen.py fix      --work work/pairs-20261123
python3 tools/pairgen.py verify   --work work/pairs-20261123 --cores 0-127 \
        --sweep-seconds 30 --fleet-seconds 60 --fleet-windows 2
python3 tools/pairgen.py report   --work work/pairs-20261123 --copy-to <dir>
```

任一阶段断言失败即非零退出，不产出 manifest —— 不存在"部分成功"的交付形态。
